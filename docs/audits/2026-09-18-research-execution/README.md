# 연구 실행의 검사·훅·되돌림·루프·재개 감사

2026-09-18 · 감사 대상: `feature/m1-research-graph`, HEAD `c89f086`와 당시 작업 트리.

## 결론

**핵심 문제는 기능을 모두 삭제한 것이 아니라, 기존 검사를 실제 Pilot 실행 경로와 연결하지 않은 채 별도 경로로 작업·완료 기록을 만든 것이다.** 원본의 단계 실행기, Pilot의 연구 그래프, 에피소드, 외부 요청 원장이 각각 존재하지만 연구 시작→검사→실행→검토→되돌림→다음 작업→마일스톤 완료를 강제하는 공통 실행 경로는 없다.

또한 원본에도 실패 상태를 승인 대기로 바꾸는 경로, 횟수 소진 후 강제 진행, 입력 버전을 확인하지 않는 재개 등 문제가 있다. 원본 전체를 그대로 되살리는 것으로 해결되지 않는다. 기존 보호 기능을 재사용하되 실제 호출과 거부·복구 동작까지 검증해야 한다.

이전 CF/PP 사례의 산출물·일부 실제 검토는 보존돼 있다. 그러나 별도 종료 스크립트로 남긴 `M1/completed`는 자동 연구 흐름의 종단 검증 증거가 아니다. 이를 M1 자동 실행 완료처럼 보고한 판단은 잘못이었다.

## 범위와 증거

- [문서 요구사항 및 파일별 검토 원장](document-requirements.md): 330개 Markdown 목록, 핵심 요구 DOC-01~30, 충돌·미완료 및 읽기 수준. 전체 정독이 아니라 전수 목록/선별 본문 검색과 핵심 정독을 구분했다. 해당 원장에 정독하지 못한 범위가 명시돼 있다.
- [원본에서 이어받은 실행기](upstream.md): 단계·계약·훅·게이트·되돌림·재개·로그 실제 호출 경로, 코드/테스트 출처.
- [현재 Pilot 실행 경로](pilot-runtime.md): 연결된 보호 기능과 호출되지 않는 검사, 완료 우회, 외부 응답 반환·후속 실행·복구.
- [UI와 보관된 CF/PP 사례](ui-and-case-trace.md): 중간 발언 지연, HEAD 기반 갱신, 단계/에피소드 불일치, 완료 스크립트.

이번 결과는 정적 코드 감사와 보관된 HEAD 읽기다. 테스트·연구 모델·외부 API를 실행하지 않았다. 운영 capability, 모든 도메인 프롬프트의 과학적 적합성, 모든 문서 문장의 무누락을 보증하지 않는다. 코드·서비스·기존 연구 데이터를 수정하지 않고 감사 문서만 추가했다.

추가 점검: [Documents·Atlas 인터페이스](documents-atlas-interface.md). 공급자 배포 기록과 소비자 접수/수신/ACK, 공통 실행기와의 연결 공백을 구분했다.

## 훅·루프·복구에서 기록할 최소 정보

기존 계약을 대체하는 새 API 명세가 아니라, 구현 계획에서 빠뜨리지 말아야 할 감사 체크리스트다.

- **시작:** project/milestone/step/work/attempt, 원래 배정과 역할, 목적·입력 참조/버전, 사용 모델·설정, 산출물/검수 기준, 정책 버전, 선행 의존성, 실행 소유권.
- **과정:** 실행 시작/대기/도구 의뢰/응답/역할 제출/공개/오류, 이벤트 ID·시각·원인 작업, 공개 가능한 발언 원문과 실제 도구 사용 기록. 모델의 비공개 내부 추론을 요구하지 않는다.
- **종료:** 구조 검사와 의미 검토를 분리한 판정, 검사기 버전, 현재 입력 적합성 재확인, 산출물 hash, 채택/한정/보류 이유, 다음 행동과 담당.
- **재작업:** 실패한 기준, 보완 내용, 원 시도와 새 시도 연결, 영향을 받는 결과, 재사용 가능한 결과, 종료 조건. 이전 실패와 대화를 삭제하지 않는다.
- **재개:** 영속 원장의 마지막 확정 상태, 미확정 외부 요청, 수신했지만 미전달/미검토인 결과, 실행 중/고아 작업, 모델 중복 실행 가능성, 채택 중복 방지. PID나 대화 기억만 믿지 않는다.
- **원자성:** 완료 판정·산출물 참조·후속 작업 생성이 일부만 저장돼도 재시작 시 안전하게 대조할 수 있어야 한다. 외부 서비스 전체에 exactly-once를 약속하지 않는다.

자연어 검토를 엄격한 schema로 만드는 것만으로 사실성이 보장되지는 않는다. 구조 검사 통과와 과학적 지지 여부를 분리하고, 핵심 주장만 필요한 깊이로 검토해야 한다. 비핵심 공백 때문에 연구 전체를 무한 대기시키지 않는다.

## 복구 순서와 완료를 판단할 증거

1. **완료 의미와 검사 연결부터 고정(G01–03).** 기존 gate/handoff 보호 기능을 점검하고 모든 완료·채택 진입점에 연결한다. 누락 입력, 검사 실패, 질문 변경 도중 반환에서 잘못된 완료가 생기지 않는지 시험한다.
2. **하나의 작업 원장과 UI 투영 연결(G09–10).** 최소한 시작·대기·발언·실패·재작업·종료가 중간에 보이게 한다. 독립 의견 장벽은 유지한다. 화면만을 위한 가짜 이벤트를 생성하지 않는다.
3. **변경 영향·후속 실행·종료 실패 루프 연결(G04–06).** 답변 저장에서 끝나지 않도록 검토→판단→추가수집/질의/설계 보완을 배정한다. 새 증거 없는 반복은 같은 결론을 계속 생성하지 말고 이유와 다음 필요조건을 남긴다.
4. **중단·정지·재개 통합(G07–08/G16).** 접수 전후, 원형 저장 후, 역할 응답 후, 최종 채택 직전 종료를 주입해 복구한다. 완료된 작업을 새 질문으로 재제출하거나 승인 기록을 만들어 복구하지 않는다.
5. **공통 품질과 산출물 연결(G11–13).** 목적별 프롬프트·검사, 실제 모델 설정 기록, 버전 있는 결과 패키지를 연결한다. 오래된 고정 단계·횟수 한도와 최신 운영 정책을 분리한다.
6. **새 격리 프로젝트로 종단 수락(G14).** 수동 종료 스크립트나 seed 완료 상태 없이 한 건을 시작하고, 의도한 실패/추가수집/되돌림/재개를 거쳐 M1 경계에서 멈추는 것을 UI와 원장에서 대조한다. 합성 수송 시험과 실제 연구 품질 시험을 따로 보고한다.

기존 CAS/멱등 요청·원형 hash/수신 저장·독립 제출 장벽·native handoff 검증은 보존 대상으로 분류한다. 수정 전 단위별로 실제 호출자와 회귀 시험을 확인해야 한다. 이번 감사 결과로 관련 코드나 문서를 추가 삭제·이동하지 않는다.
