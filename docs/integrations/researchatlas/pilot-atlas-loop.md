# Pilot–Atlas 자동 연구 왕복

2026-09-13. 사용자 요청에 따라 기존 Atlas 담당과 함께 진행한다. 공동 목표는 연구 쟁점 → 자체 완결 질문 → Atlas 답변·근거 → 독립 검토 → 교차 반박 → 다음 질문 또는 연구 방향 결정이다.

## 구현 순서와 완료 기준

| 단위 | 담당 | 결과와 완료 기준 | 상태 |
| --- | --- | --- | --- |
| 1. 답변 재개와 입력 고정 | Pilot, Atlas 생산자 검토 | 같은 요청을 재개하여 QA를 수신하고 검토 입력을 고정. 종료 실패·QA 부재·중복 등록·중단을 구분 | 소비자 구현·시험 완료, Atlas 재검토에서 AL-R1–R3 해소 확인 |
| 2. 연구 쟁점 연결 | Pilot | 현재 정식 질문/쟁점/결정 참조와 의뢰 목적을 고정. 전제가 바뀌면 기존 요청을 바꾸지 않고 새 요청으로 연결 | 구현·실제 질문 접수 검증 완료 |
| 3. 검토 실행 연결 | Pilot | 동일 입력으로 분야·방법·반증 담당 초기 의견을 독립 작성. 전원 제출 후 공개해 반박·최종 의견을 기존 council 명령에 등록 | 구현·실제 9발언 등록 완료 |
| 4. 다음 행동 연결 | Pilot, Atlas 의미 검토 | 근거·반론·미해결 문제를 연결한 결정. 새 질문은 이전 QA와 판단 영향을 포함. 정보 부족이면 외부 탐색·범위 축소·보류를 구분 | 조정자 결정·다음 자료 확보 행동 등록 완료 |
| 5. 실제 왕복과 UI | 공동 | 질문 이유→Atlas 답변→실제 검토 대화→결정 변경을 기존 화면에서 확인. 합성 실행 시험과 실제 연구 판단을 구분 | 기존 UI에서 실제 결정·3회차 대화 확인 완료 |

단위 1은 과학적 판단을 생성하지 않는다. `review_input_ready`는 검토 입력을 준비했다는 뜻이다. 후속 구현은 아래 단위 2–4와 실제 실행 결과를 따른다. 정식 질문 선택과 최종 과학적 결론 작성은 조정자가 수행하며, 임의 쟁점 선택부터 무한 재탐색까지 수행하는 상시 스케줄러는 아니다.

## 첫 구현 단위

`research atlas-service advance ROOT --key REQUEST_KEY --watch --interval 10 --json`

기존과 같이 서버 측 `PILOT_ATLAS_CONNECTION_FILE`을 설정한다. 연결 파일 경로·토큰은 질문이나 브라우저에 전달하지 않는다. `ask`로 접수한 요청 또는 접수 응답 유실 후 journal에 남은 요청을 대상으로 한다.

- queued/running: 진행 상태를 반복 확인한다. `--watch`가 없으면 한 번 관찰한 뒤 반환한다.
- 종료 상태에 QA 없음: `needs_attention`과 `terminal_qa_missing`을 반환한다. 실패 작업을 새 키로 자동 재실행하지 않는다.
- 종료 상태에 QA 있음: 기존 수신·해시 검증·근거 등록 후 입력 묶음을 저장한다. failed/partial/interrupted도 원래 상태를 보존한다. QA 수신은 결과의 과학적 적합성을 뜻하지 않는다.
- 프로세스 중단·통신 오류: 원격 작업을 취소하지 않는다. 같은 키로 재개한다. 오류는 숨기지 않고 호출자에게 반환한다.
- 연구 HEAD 충돌: 기존 optimistic concurrency 오류를 보존한다. 저장한 QA로 다시 등록할 수 있다.
- 동시 advance: 연구별 잠금을 사용한다. 다른 advance 실행이 있으면 retryable 오류로 반환한다.
- 검토 입력 작성 이후 재호출: 저장한 입력의 해시를 확인해 반환한다. Atlas 재호출·QA 재등록을 하지 않는다.

검토 입력은 `.atlas-link/objects/<sha256>`의 불변 JSON으로 저장한다. journal의 `review_input_sha256`이 이를 가리킨다. 질문 원문·실제 전송 질문·이전 요청·프로젝트 바인딩·Atlas 실행 상태·QA 원형 참조·Pilot 근거 참조·참고 자료 수신 결과를 포함한다. 이후 참고 원문 재수신은 이 입력을 변경하지 않는다. 새 입력 버전으로 검토하는 동작은 후속 단위에서 구현해야 한다.

검토자가 QA 텍스트를 제공받는 것과 PDF 원문을 직접 읽는 것은 다르다. 이 입력은 QA의 분석 내용과 참고 원문 참조를 제공하며, 별도의 원문 읽기 증거를 만들지 않는다. 초기 입력에는 다른 검토자의 의견을 넣지 않는다.

## 확인 결과

- 관련 Python 회귀 117개 통과. 이전 전체 회귀 671개는 이 기능 추가 전 기준이며 합산하지 않는다.
- 기존 실제 T1 답변 두 건으로 CLI advance를 각각 두 번 실행했다. 동일 입력 해시가 반환되고 시험 연구 HEAD는 변하지 않았다. 신규 Atlas 질문·과학적 검토·M1 완료를 생성하지 않았다.
- 질문 1 입력: `b1d369cd07a2ce26d6c1d630035ea891b16f287de87b31d61352d52fbec71646`.
- 후속 질문 2 입력: `f7c5b5ffe17bc9c9b18f9a45e40e9a28a5ccfff92ef6359f21e6001ab55bae0e`.
- 실행 증거: `output/evaluations/pilot-atlas-t1/advance-verification.json`.
- 이번 단위는 CLI 기능이다. UI 서버를 교체하거나 자동 수신 버튼을 추가하지 않았다. 기존 UI에서 근거 등록 기록을 조회하는 기능은 유지된다.

## Atlas 공동 검토 반영

[Atlas 회신과 L01–L10 수락 시험안](atlas-loop-reply.md)을 확인했다. 현재 A1에서 생산자 필수 변경 없이 첫 연결 단위를 구현할 수 있다는 판단을 수용한다. 다음 사항을 재현하는 테스트를 추가해 수정했다.

- AL-R1: 명시적 실행 예약 부재/dispatch 오류는 정상 대기가 아닌 진단으로 반환한다. running의 scheduled=false만으로 종료를 단정하지 않는다.
- AL-R2: 새 검토 입력에는 job/receipt/fingerprint와 issues/error/dispatch 상태, 실패 시 진단·제한 검토 목적을 포함한다.
- AL-R3: 수동 수신했거나 QA를 저장한 경로에서도 최초 입력 고정 전 terminal 상태를 확인한다. 저장한 terminal QA의 오프라인 재개를 유지한다.
- 추가 확인: active 때 수신한 QA와 이후 terminal의 QA 참조가 달라지면 기존 QA를 최종 답변으로 고정하지 않는다.

신규 입력은 **schema_version=2**다. 위 실제 T1 재사용 시험에서 먼저 만든 schema 1 입력 두 건은 역사 기록으로 보존하며 자동 수정하지 않는다. 실행 진단 필드가 추가된 schema 2의 분기·고정 검사는 합성 Atlas와 실제 Pilot journal/import로 검증했다. 새로운 실제 Atlas 질문 또는 schema 2의 전체 연구 왕복을 완료했다고 집계하지 않는다.

Atlas 담당 터미널의 재검토 답변에서 AL-R1–R3 해소, 최신 테스트 23개와 추가 경계 확인 7개 통과를 확인했다. 이는 Pilot 회귀 117개와 중복되므로 합산하지 않는다. L01/L06/L08 전체 수락은 후속 연구 쟁점·council 연결 뒤 수행한다.


## 단위 2–4 구현과 실제 왕복

`ask-question ROOT --key KEY --question-id REGISTERED_ID [--previous KEY]`는 정식 external_question과 연결 결정에서 의뢰 목적·공백·판단 영향·범위를 구성한다. 질문 원기록과 참조는 Pilot journal/공통 입력에 보존하며 미지원 Atlas 필드로 전송하지 않는다. 같은 키는 새 연구 상태로 다시 구성하지 않는다.

`advance ROOT --key KEY --watch` 이후 `review ROOT --key KEY --host /absolute/path/to/codex`로 세 역할의 initial/response/final을 실행·재개한다. 위 명령은 모두 `research atlas-service` 하위 명령이며 기존 연결 파일 환경 설정을 사용한다. 공통 입력·역할별 packet·원응답·실행 이벤트·정식 제출 영수증을 저장한다. 초기 의견을 전원 제출한 뒤 공개한다. 완료 역할을 다시 실행하지 않으며 실행 중/실패 시도는 보존·진단한다. 도구 접근·미완료 host 이벤트를 정상 의견으로 대체하지 않는다.

`outcome ROOT --key KEY --file DECISION_JSON`은 완료 협의의 최종 3개 참조에 조정자가 작성한 결정과 다음 행동을 연결한다. 선택적으로 다음 정식 질문을 등록할 수 있지만 새 Atlas 모델 작업을 자동 제출하지 않는다. `collect_materials`일 때는 새 자료 확보가 다음 작업이다. 유효하지 않은 원기록 참조는 입력을 고정하기 전에 거절하고, 유효하게 수락한 입력만 재개·변경 충돌을 적용한다.

[실제 Abbasi 측정 방향 왕복](../../research/2026-09-10-polymer-sdl/atlas-service-loop/README.md): 정식 질문→새 Atlas QA→원형 수신→3역할×3회차→기존 D2에 연결된 새 결정까지 완료했다. 다음 행동은 외부 자료 확보이며 같은 질문을 추가 실행하지 않았다. UI에서 결정과 실제 대화를 확인했다. 코드 경로 검증과 실제 과학적 적용 판단을 이 기록에서 구분한다.

Atlas의 §10 단위 2–3 검토에는 남은 필수 수정이 없었고, outcome의 O-R1은 선제 도메인 검증으로 수정 후 §12에서 해소를 확인했다. 생산자 변경은 없었다. 관련 Python 132개·기존 council/외부 노드 연결 36개·UI 14개 검사 통과. 전체 연구 자동화 또는 M1 완료를 뜻하지 않는다.
