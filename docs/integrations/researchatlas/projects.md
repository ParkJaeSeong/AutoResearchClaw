# 프로젝트 생성·연결과 자료 소속

[전체 흐름](README.md) · [계약](contracts.md) · [작업 단위](tasks.md)

2026-09-13 제안. 기존 Atlas 프로젝트·queue·source 구조를 재사용한다. 이 문서 작성으로 프로젝트나 연결을 실제 생성하지 않았다.

## 언제 생기는가

Pilot 연구 프로젝트는 사용자의 연구 요청을 접수할 때 생성한다. 이미 진행 중인 연구라면 기존 프로젝트에서 이어간다. Atlas 연결은 첫 프로젝트 범위 조회·질문·자료 전달 전에 선택한다. 적절한 Atlas 프로젝트를 찾기 위한 전체 현황·목록 조회는 연결 전에도 가능하다.

1. Pilot이 목표·범위·제약을 가진 연구 프로젝트를 만든다.
2. `atlas_projects` / `GET /api/projects`로 기존 Atlas 프로젝트를 확인한다.
3. 제목만으로 동일 연구라고 단정하지 않고 본문·범위·연결 자료를 조회해 적합한 프로젝트를 선택한다.
4. 없으면 Atlas 프로젝트를 새로 만든다. 현재 CLI 생성은 있지만 HTTP/MCP 생성은 미노출이다.
5. Pilot에 두 프로젝트의 ID와 선택 이유·적용 범위를 저장한다.
6. 이후 의뢰는 연결한 Atlas 프로젝트와 별도의 Pilot 문맥 참조를 포함한다.

연구 질문이 조금 바뀔 때마다 새 프로젝트를 만들지 않는다. 연구 목적·실행 책임이 독립적으로 분리될 때 Pilot 프로젝트 분리를 판단한다. Atlas 프로젝트는 지식의 정리 범위에 따라 재사용·분리한다.

## 두 프로젝트의 차이

| 구분 | Pilot 연구 프로젝트 | Atlas 지식 프로젝트 |
| --- | --- | --- |
| 목적 | 연구를 판단하고 수행 | 관련 지식·자료·분석을 정리 |
| 주요 기록 | 질문·가설·독립 의견·쟁점·결정·실험·인계 | 연결 자료·위키·QA·분석·미확인 지식 |
| 식별 | Pilot project ID | Atlas project ID |
| 변경 | 연구 범위·설계 수정 이력 | 자료 연결·지식 갱신 이력 |
| 완료 | M1/M2/M3 판단 | 정리 상태이며 Pilot 완료와 별개 |

여러 Pilot 연구가 하나의 Atlas 지식 프로젝트를 사용할 수 있다. 첫 연결은 **Pilot 연구마다 기본 Atlas 프로젝트 하나**를 정한다. 다른 분야 지식은 별도 검색·참고 관계로 연결하고, 기본 프로젝트 변경 이력을 보존한다. 복잡한 다대다 실행 라우팅은 첫 버전에 요구하지 않는다.

예: Atlas의 ‘고분자 복합소재’를 Pilot의 ‘제조 조건–전도도 비교’와 ‘기계적 물성 예측’이 함께 사용한다. 각 Pilot 연구의 가설·결정·근거 묶음은 독립적으로 유지한다.

## 연결 계약 제안

Pilot의 연결 기록: `pilot_project_id`, `atlas_instance_id`, `atlas_project_id`, `purpose`, `scope`, `selection_reason`, `previous_binding_ref`.

`atlas_instance_id`는 자료실에 저장하는 비밀이 아닌 고정 ID를 info API/MCP로 노출하는 최신 공동 결정안을 따른다. 로컬 별칭은 표시용이며 영속 ID를 대신하지 않는다. 재시작·포트·토큰 변경 후에도 같은 자료실이면 ID를 유지한다. 구현 전 연결 파일의 URL/token만으로 동일 자료실임을 보장할 수 없으며, 다른 instance ID를 확인하면 자동 의뢰하지 않는다.

Atlas 요청의 `project` 또는 향후 `project_id`는 Atlas ID다. `client_context` 안의 Pilot 프로젝트·질문·쟁점·회차는 불투명 참조이며 Atlas 권한·실행 설정이 아니다. 두 프로젝트의 이름이 같아도 ID를 교환해 사용하지 않는다.

기본 연결을 바꾸면 새 요청부터 새 연결을 사용한다. 이미 접수한 job, QA, 분석, 근거 묶음은 원래 연결을 유지한다. 프로젝트 이름 변경은 새 연구나 새 자료 버전으로 처리하지 않는다. 연결 대상이 사라졌거나 유효하지 않으면 명시적으로 실패하며 전체 자료실로 조용히 확대하지 않는다.

## 자료의 소속

원본 바이트는 자료실의 공용 보관·중복 제거 규칙을 따른다. 프로젝트에는 자료·버전과 연구상 관련성을 연결한다. 같은 자료를 두 프로젝트가 사용한다고 원본을 두 번 복사하거나 독립 논문 두 편으로 세지 않는다.

현재 queue의 `projects`·`contexts`·`receipts`는 활용 가능한 기반이다. 접수 초기에는 `input_id + sha256`만 있고 `source_id/version=null`일 수 있다. 정리 후 확정한 source 매핑과 프로젝트 연결을 돌려준다. 이미 보관된 source와 아직 정리 전 input에 대한 연결 작업을 구분한다.

Atlas `project_attach`는 source 버전 연결을 지원한다. 버전을 생략한 재연결은 기존 버전을 유지할 수 있으므로 자동 최신 갱신으로 해석하지 않는다. Pilot의 근거 묶음은 프로젝트의 현재 자료 목록 대신 정확한 source/page/QA 버전을 고정한다.

자료가 다른 프로젝트에도 연결돼 있다는 사실만으로 해당 연구의 주장까지 가져오지 않는다. 사용 목적·발견 이유·조건 적합성은 각 Pilot 연구에서 다시 판단한다.

## 범위 검색과 우연한 발견

Atlas의 일반 자료·질문은 project=null을 계속 허용한다. 기본 프로젝트 필수는 Pilot M1 운영 규칙이며 Atlas 서비스 전체의 제약으로 확대하지 않는다. Pilot M1 의뢰는 기본 프로젝트 범위를 명시한다. 첫 연결에서는 다른 분야 탐색을 별도 조회로 구분하고 결과를 ‘범위 밖 참고 후보’로 표시한다. `atlas_search`의 project/project_only를 명시한다. 선택 프로젝트에서 project_only=false는 공용 wiki를 보완하며 다른 프로젝트 전용 페이지까지 포함하지 않는다. 다른 프로젝트의 해석은 그 프로젝트를 별도 조회한다. 이 필터를 작업 전체의 접근 격리로 설명하지 않는다. 현재 ask의 프로젝트 문맥과 v1 analyze의 엄격한 지정 근거 계약은 구분한다. analyze 구현·배포 여부는 capability로 확인한다.

범위 밖 후보는 Pilot이 관련성을 판단한 뒤 자료 연결·다음 근거 묶음 편입을 요청한다. 이 과정에서 원래 프로젝트·출처를 유지한다. 전체 자료실을 한 번에 LLM 입력으로 보내지 않고 검색·페이지네이션·선택 조회를 사용한다.

프로젝트는 현재 접근 권한 경계가 아니다. 미공개 초기 의견은 Pilot에 보관하며 Atlas 공용 질문에 보내지 않는다.

## 필요한 서비스 보완

- 프로젝트 생성: `POST /api/projects` / `atlas_project_create` 제안. 요청 키와 내용의 충돌 처리 필요. 현재 내부 title 기반 재사용만으로 같은 키·다른 범위의 충돌이 해결되지는 않는다.
- 기존 input 또는 source의 프로젝트 연결: 기존 `Workflow.attach` / `Library.project_attach`를 서비스에 노출하는 방향. 대상 종류·명시 버전·연결 이유를 구분하고 정확한 경로는 계약 단계에서 확정한다.
- 연결 확인: 기존 목록·페이지 조회를 재사용하고 Pilot에 ID 대응을 저장한다. 별도 양방향 프로젝트 동기화 서버는 만들지 않는다.

T1은 **이미 있는 Atlas 프로젝트를 명시적으로 선택**해 먼저 시험할 수 있다. 프로젝트 생성 API의 개발을 기다리며 동일 프로젝트를 임시로 복제하지 않는다. 기존 프로젝트가 없는 환경의 완전 자동 시작에는 생성 계약이 필요하다.
