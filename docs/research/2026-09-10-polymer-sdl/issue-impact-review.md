# 22개 쟁점의 영향과 다음 작업

기존 쟁점 22개와 해소 조건을 읽어 **8개 작업 묶음**으로 분류했다. 같은 원문·표를 확인해야 하는 일은 함께 처리한다. 각 쟁점의 원래 기록과 해소 조건은 보존한다. 이것은 조정자의 작업 제안이며 새 에이전트 합의나 검증 결과가 아니다.

## 무엇을 준비하고 무엇을 보류하나

| --- | ---: | --- | --- |

첫 우선순위는 **H1 데이터 조건과 평가 명세**다. 기존 감사 결과를 재사용하고, 남은 확인이 어떤 자료 사용 결정을 바꾸는지 명시한다. H2의 기전 검증 보류가 다른 요구사항 작성이나 자료 수집을 막지 않도록 작업을 구분한다. 자료를 확인하지 못하면 해당 값·용도·가설의 보류 또는 범위 축소를 기록한다.

## 실제 구현·등록 범위

- `issue.impact.record`로 22개 영향 분류를 정식 연구 기록에 등록했다. 각 분류에는 원래 쟁점 참조, 영향받는 자료·가설, 준비/보류 작업, 다음 확인, 확인되지 않을 때의 처리, 담당 역할과 이유가 있다.
- 입력은 `.superpowers/research/2026-09-10-polymer-sdl/issue-impact-input.json`이다. 필드에 적힌 자료·가설 이름은 영향 대상 설명이며 사용 적합성을 검증한 증거 참조는 아니다.
- 동일 내용과 동일 쟁점·단계 버전은 기존 분류 ID를 재사용한다. 분류가 바뀌면 이전 내용을 보존한다. 쟁점의 상태 변경이나 정식 단계 개정 후에는 이전 제안을 현재 제안으로 표시하지 않는다.
- UI 요약에서 8개 작업 묶음을 보고, 각 쟁점의 **어떤 작업에 영향을 주나요?**에서 분류 이유와 다음 확인을 볼 수 있도록 연결했다. 원래 단계 차단 범위도 함께 유지한다.

**R2는 영향 분류의 기록·조회까지 구현했다. 차단 범위 변경과 진행 조건 적용은 아직 남았다.** 여러 쟁점의 해소 조건은 질문 설계를 계속하도록 허용하지만, 기존 `blocking_scope`는 questions 전체를 차단한다. 이 차이는 분류 문구만으로 해소하지 않는다. 다음 구현은 분류에 대한 검토와 차단 범위 변경 이력을 연결하는 경로다. 원래 쟁점을 해결 처리하거나 승인 기록을 생성하지 않는다.

## 검증과 한계

영향 분류 테스트 11개, 수집 테스트 13개, viewer 테스트 4개, UI 테스트 18개가 통과했다. 테스트는 등록 원자성, 정확한 참조, 과거 기록 보존, 상태 변경 시 제안 재검토, 기존 쟁점·노드 판단 보존을 확인한다. 과학적 효과 검증이 아니다.

실제 API의 22개 분류·8개 묶음과 제공 JS, 이전 HEAD의 분류 미등록 상태를 확인했다. 결과는 연구 작업 공간의 `issue-impact-receipt.json`에 남겼다. 브라우저 시각 검수는 이전 연결 도구 오류가 남아 완료하지 못했다. 화면 폭·테마별 배치와 실제 키보드 동작은 확인했다고 주장하지 않는다.
