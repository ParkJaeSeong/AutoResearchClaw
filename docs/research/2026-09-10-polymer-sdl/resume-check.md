# 새 M1 기준으로 재개하기

2026-09-11 최초 점검(아래 R1 구현 전 상태). 기준은 루트 `AGENTS.md`다. 기존 연구의 HEAD `3b54dd2ac433bc8eedc04090e54c20e57b4586e0679ba3383560b909e58f43e8`에서 질문 4차 검토까지 보존돼 있다. 열린 쟁점은 22개다. 질문은 필수 쟁점 때문에 진행 불가, 검색·선정은 이전 입력에 묶여 재검토 필요, collect 이후는 미시작이다.

## 현재 구현과 다른 점

1. `m1_nodes.py`는 scope부터 review까지 9개 노드이며 review 다음이 handoff다. `handoffs.py`도 이 9개만 묶는다. 실험 설계·실행 준비가 새 M1 완료 조건으로 연결되지 않았다. 기존 `validation_design.py`와 `resource_planning.py`는 이전 단계용 구현이므로 그대로 연결됐다고 볼 수 없다.
2. `m1_nodes.register_node`는 앞 단계의 준비 완료를 요구한다. 질문에 묶인 미해결 문제가 검색·선정 갱신과 수집 등록에도 영향을 준다. 수집 사실과 사용할 수 있다는 판단을 분리할 정식 경로가 필요하다.
3. `m1_search.decide_corpus`는 명시적 사용자 결정을 기록하는 경로다. 사전 허용 범위 안의 에이전트 선정과 사용자 승인 기록을 구분하는 경로가 필요하다. 기존 승인을 만들어내거나 gate를 끄지 않는다.
4. 현행 연구 viewer는 읽기 전용이다. 새 설계·준비 상태와 결론 버전별 선택적 피드백도 아직 연결해야 한다.

## 작게 나눈 후속 작업

각 행은 별도 구현·검증 단위다. 이 표는 우선순위와 완료 기준이며, 해당 기능이 구현됐다는 뜻은 아니다.

| 순서 | 작업과 주 변경 위치 | 완료를 확인할 방법 |
| --- | --- | --- |
| R1 | `m1_evidence.py`와 native CLI: 선정 전 수집 사실 등록 경로. 출처·버전·접근 범위·해시를 불변 기록으로 보존하고, 기존 collect의 선정 자료 커버리지 검증은 유지 | 질문이 막혀도 수집 사실 저장 가능. 수집만으로 사용 가능·extract·M1 완료가 되지 않음. 같은 파일 재개 시 중복 생성 방지 |
| R2 | `issues.py`, `m1_nodes.py`: 쟁점의 영향 작업을 명시적으로 재검토하는 경로 | 단위 미확정 자료의 학습은 막고 관련 없는 수집은 허용. 과거 쟁점과 변경 이유 보존. 기존 22개를 자동 해결하지 않음 |
| R3 | `m1_search.py`, 승인 계약·CLI: 사전 허용 범위에 근거한 선정 판단 | 범위 내 자율 결정과 실제 사용자 승인을 구분. 범위 밖·만료·다른 입력 버전은 거부 |
| R4 | `m1_nodes.py`, 새 설계 계약: 가설 이후 실험 설계와 근거 연결 | 변수·대조·분할·측정·분석·성공·중단 기준 누락 검출. 가설 개정 시 의존 설계 재검토 |
| R5 | 새 실행 준비 계약과 `handoffs.py`: 자원·권한·실행 명세·사전 점검을 인계 필수 조건으로 연결 | 필수 미확정·오래된 점검으로 인계 불가. 비적용 이유 기록. 사전 점검이 실제 실험을 실행하지 않음. 기존 기록은 보존하되 새 기준 완료와 구분 |
| R6 | `research_ui`와 viewer: 수집/사용 판단, 설계/준비, 되돌림과 단계 결론 표시 | 실제 API와 화면에서 현재 판단·이유·다음 일이 일치. 과거 9단계만 통과해 새 M1 완료로 표시하지 않음 |
| R7 | 별도 피드백 기록 경로와 UI: 결론 버전에 연결한 선택적 피드백 | 무응답이어도 허용 작업 진행. 접수→영향 판단→재검토→처리 이유 추적. 피드백을 승인으로 변환하지 않음 |

R1 뒤 실제 확보 자료부터 등록한다. R2·R3 뒤 검색·선정의 현재 입력을 갱신하고, 근거 추출·종합·가설 검토로 잇는다. R4·R5 뒤 실험 준비를 검토한다. 실제 확인되지 않은 기준을 충족으로 표시하지 않는다.

## 이번 재개의 산출물

- 기존 공개 파일 5개를 원래 경로와 해시로 묶은 `m1-preparation-intake.json`: Abbasi 원문과 공개 저장소 자료, 두 출처 묶음이다. 새 문헌 5편을 찾은 것이 아니다.
- [실험 착수 준비 초안](experiment-preparation.md): H1–H3의 준비·보류 범위, 비교 계획과 필수 미확정 사항.
- 기존 연구는 재시작하거나 쟁점을 해결 처리하지 않았다. UI 상태나 런타임 기능을 변경한 작업도 아니다.


## R1 구현·실제 등록 결과

- `m1.source.capture`를 추가했다. 기존 단계·승인 조건과 별도로, 파일 바이트와 제공 해시를 비교해 불변 객체 저장소에 보존한다. 출처·버전·읽은 범위는 제공자의 기록이며 출처 인증이나 과학적 검증 완료가 아니다.
- 동일한 입력은 같은 수집 ID를 재사용한다. 파일 또는 읽기 기록이 달라지면 새 기록을 만들고 이전 기록을 보존한다. 같은 command-id 재시도는 새 HEAD를 만들지 않으며, 다른 command-id의 동일 자료 등록은 이벤트만 추가하고 자료를 중복 생성하지 않는다.
- 실제 파일 5개를 등록했다. HEAD는 `908f129e1fcfb003624487fc01de73dd9c562e651283ae819916e9ab18e83b5a`다. 원래 연구 상태는 수집 목록 추가 외에 전부 동일하며 열린 쟁점 22개를 유지한다. 기존 collect 단계 완료나 사용 승인을 생성하지 않았다.
- UI에 읽은 범위·남은 확인 사항·출처 연결을 추가했다. 원시 파일 바이트는 공개 API로 자동 노출하지 않는다. 과거 HEAD에서는 해당 시점에 등록된 수집 자료만 보인다.
- 검증: 수집 테스트 13개, 기존 view/viewer 테스트 13개, UI 테스트 17개 통과. API의 5개 기록과 실제 제공 JS 파일을 확인했다. R1 수정 전 기존 M1 회귀 테스트 84개도 통과했다.
- 화면 자동 확인은 미완료: 연결된 브라우저가 없고 Orca CLI가 `Unable to determine Orca.app path from symlink: /usr/local/bin/orca`로 실패했다. 화면 폭·테마·실제 키보드 동작은 확인했다고 주장하지 않는다.
- UI 가이드 U2의 수집 기록 연결에 해당한다. CSS나 단계 완료 표시는 변경하지 않았다. 다음 구현은 R2의 쟁점 영향 범위 재검토다.

등록 형식과 재시도 방법: [자료 수집 CLI](../guides/source-capture.md).
