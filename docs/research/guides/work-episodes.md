# 작업 회차 기록 사용법

작업 회차는 하나의 질문이나 재검토 목적을 수행한 기록이다. 단계는 작업의 종류이며, 회차 번호는 프로젝트에서 시작한 순서다. 같은 단계로 돌아오면 새 회차를 만들고 이전 회차와 이유를 연결한다.

이번 구현은 명시적으로 등록한 회차의 저장·조회와 개발 검토 규칙을 제공한다. 현재 정식 연구 질문의 Atlas 요청·수신과 근거 검토 실행이 회차를 자동 생성한다. 다른 실행 경로는 명시적으로 등록한다. 과거 단계 기록을 추정으로 변환하지 않는다.

## 저장과 명령

기준 기록은 프로젝트의 `.researchclaw/research_graph/` 불변 저장소에 있다. 모든 명령은 기존 `research apply`를 사용한다. 조회한 HEAD를 전달하며, 응답이 유실됐으면 같은 내용과 command-id로 재요청한다. 같은 키로 다른 내용을 보내면 거절된다.

```sh
researchclaw-codex research inspect ROOT --json
researchclaw-codex research apply ROOT --operation episode.start \
  --payload start.json --expected-head HEAD --command-id episode-search-start --json
```

`start.json` 예시:

```json
{
  "id": "initial-search",
  "stage": "자료 탐색",
  "title": "복합재 전도도 비교에 필요한 자료 찾기",
  "purpose": "충전재 함량과 가공 조건을 비교할 근거를 확보한다.",
  "depends_on": [],
  "return_to": null,
  "return_reason": null,
  "review_required": true
}
```

검토 여부는 회차마다 명시한다. 개발 중에는 `true`를 사용한다. 프로젝트 전체 기본값과 기존 실행기에 자동 적용하는 기능은 아직 없다.

| 명령 | 입력 | 의미 |
| --- | --- | --- |
| `episode.note` | id, kind, author, text | 진행 중인 회차에 공개 가능한 원문 보고 추가 |
| `episode.conclude` | id, execution_status, judgment, remaining, next_action, next_reason | 작업 종료·실패와 판단을 별도 기록 |
| `episode.review` | id, decision, reviewer, feedback | 종료된 결과에 개발 검토 한 번 기록 |

`kind`는 `dialogue`·`tool`·`output`, 종료 상태는 `finished`·`failed`, 검토 결정은 `continue`·`revise`다. 의견과 도구 보고는 제출 순서로 보존한다. 현재 산출물은 텍스트 기록이며 파일 첨부·원응답 참조의 자동 연결은 다음 작업이다. 미공개 독립 의견, 토큰 등 비밀을 note에 넣지 않는다. 기존 council의 공개 순서를 우회해 복사하지 않는다.

종료 후 원 회차에 발언이나 결론을 덮어쓸 수 없다. 수정할 때는 새 회차를 만들고 `return_to`에 이전 ID, `return_reason`에 이유를 남긴다. 개발 검토의 reviewer는 로컬 CLI 사용자의 선언이며 인증된 사용자 서명이 아니다. 에이전트가 사람 대신 검토를 생성하면 안 된다.

## 의존성과 검토

`depends_on`은 실행 전에 결과가 필요한 회차다. 대상 회차가 작업을 마치고, 검토가 필요하다면 `continue`를 받은 뒤 새 회차를 시작할 수 있다. 대기·실패·수정 요청 상태인 결과에 의존하면 시작을 거절한다. 관계없는 회차는 계속 시작할 수 있다.

`return_to`는 다시 살펴보는 대상이다. 실행 의존성과 다르므로 수정 요청을 받은 결과를 재검토할 때도 연결할 수 있다. 수행 순서나 같은 단계명으로 의존 관계를 추정하지 않는다.

개발 검토는 다음 흐름을 허용하는 기록이다. 과학적 주장의 승인이나 M1 완료, 실험 실행 권한이 아니다. 기존 연구 실행기의 모든 명령을 차단하는 기능도 아니다.

## 화면

연구 과정에서 최근 시작한 회차부터 보여준다. 카드를 펼치면 목적·판단·남은 문제·다음 작업과 이유, 공개된 진행 보고, 산출물 기록을 볼 수 있다. 작업 상태는 기록된 보고이며 실제 에이전트 프로세스의 생존 확인이 아니다.

브라우저에서 회차를 생성하는 기능, 나머지 실행 경로 연결, 큰 기록의 상세 지연 조회, 프로젝트 `work/` 아래 Markdown 내보내기는 후속 구현이다.

## Atlas 검토 자동 기록

`research atlas-service review`의 새 검토 실행은 한 개의 회차를 자동으로 만든다. 기존의 세 역할·세 라운드를 실행하며, 각 라운드의 정식 의견이 모두 등록된 뒤 회차에도 원래 발언을 표시한다. 원래 council의 미공개 경계를 유지한다.

이미 수신한 Atlas 답변의 입력 해시와 근거 참조, 9개 의견, 최종 의견 분포와 원문 참조가 남는다. 동일 요청을 재개해도 회차·의견을 다시 추가하지 않는다. 완료된 과거 결과에 새 회차를 소급 생성하지 않는다.

검토 실행이 끝나면 작업 종료·개발 검토 대기다. 이 연결은 검토자 의견을 과학적 결론이나 사용자 승인으로 바꾸지 않는다. 기존 다른 실행 명령까지 개발 검토를 강제하는 연결과 Atlas 요청·대기·실패의 전체 도구 이력은 다음 구현이다. 중단된 검토의 실시간 생존 감지는 아직 없으며 실행 기록을 확인한 뒤 동일 요청으로 재개한다.

## Atlas 요청과 검토의 구분

정식 연구 질문을 보내는 `ask-question`과 답변을 가져오는 `advance`는 요청 회차 하나를 공유한다. 전송 준비·접수·응답 대기·확인 필요·수신을 기록한다. 동일 상태의 반복 조회는 중복 발언으로 쌓지 않는다. 전송 오류에서 서버가 접수했는지 불명확하면 실패 확정으로 표시하지 않고 같은 키로 확인한다.

요청 회차는 자료 수신이 목적이므로 개발 검토를 필수로 두지 않는다. 뒤의 근거 검토 회차가 과학적 사용 범위를 검토하고 개발 검토를 기다린다. 부분 답변과 실패 진단 자료는 정상 연구 답변과 구분한다. 토큰·원래 예외 전문·미공개 대화는 자동 기록하지 않는다.

이 자동 기록은 정식 연구 질문 경로에 적용한다. 일반 `ask`·`poll`·`receive`를 직접 호출한 모든 이력을 자동 추적하지 않으며 이미 끝난 과거 요청을 소급 변환하지 않는다.

## 화면에서 개발 검토 저장

종료한 검토 회차를 펼치고 의견을 적은 뒤 **계속 진행** 또는 **수정 요청**을 선택한다. 계속 진행은 해당 결과에 의존하는 다음 회차를 시작할 수 있다는 뜻이다. 수정 요청은 그 결과에 의존하는 작업을 대기시키고 재검토가 필요함을 남긴다. 버튼 자체가 에이전트나 실험을 실행하지 않는다.

검토는 종료된 결과에 한 번 저장한다. 과거 기록을 보는 중에는 저장할 수 없다. 저장할 때 다른 작업이 기록을 갱신했다면 최신 내용을 확인한 뒤 다시 제출한다. 전송 결과가 불확실할 때는 **같은 요청 다시 확인**으로 원래 내용을 재확인한다. 성공한 검토를 새 요청으로 중복 제출하지 않는다.

저장한 의견은 원래 결론을 덮어쓰지 않는다. 후속 계획은 자동 저장한다. 담당 배정과 실제 재검토 회차의 시작은 다음 구현이다. 로컬 UI 입력은 `local-ui-user`로 표시하며 별도 사용자 인증이나 전자서명이 아니다.

## 검토에서 후속 계획으로

새 검토를 저장하면 후속 계획도 같은 시점에 저장된다. **계속 진행**은 원 결론의 다음 작업과 이유를 사용하고, **수정 요청**은 원 회차를 재검토할 계획과 사용자의 의견을 연결한다. 원 결론·발언을 바꾸지 않는다.

계획은 검토 카드 안에서 확인한다. 계획됨·실행 전으로 표시하며 실제 수행 회차 수나 순번에는 포함하지 않는다. 선행 작업이 실패했다면 계속 진행 의견을 받더라도 해당 후속 계획은 차단 상태로 남는다.

원 결론과 검토의 해시를 함께 보존해 어떤 결과에서 나온 계획인지 확인한다. 과거 검토에 계획을 소급 생성하지 않는다. 실행할 단계·담당·도구를 정하고 새 회차로 연결하는 것은 다음 조정자 작업이다.
