# 연구 UI 가이드라인

시각 디자인은 [공통 표준 적용표](visual-design.md)를 기준으로 한다. 색상·서체·간격·패널·반응형 규격과 구현 위치를 함께 관리한다.

이 UI의 목적은 사용자가 **지금 연구가 어디에 있고, 왜 그런 판단을 했으며, 다음에 무엇을 해야 하는지** 이해하게 하는 것이다. 연구·개발 용어를 모르는 사용자도 주요 흐름을 읽을 수 있어야 한다.

이 문서를 M1·M2·M3 UI의 공통 기준으로 사용한다. [화면·컴포넌트 규칙](components.md)은 구현 기준, [검수와 적용 목록](review.md)은 변경 완료 판단 기준이다. 연구 판단 자체는 [연구 운영 가이드](../research/guides/README.md)를 따른다.

## 1. 첫 화면이 답해야 하는 질문

1. 무슨 연구인가?
2. 지금 무엇을 하고 있으며, 실제 실행 중인가?
3. 최근에 무엇을 확인하거나 결정했는가?
4. 무엇이 남았고 다음 행동은 무엇인가?
5. 그 판단의 대화와 근거는 어디서 볼 수 있는가?

문헌 수·제출 수·내부 ID보다 위 질문에 대한 답을 먼저 보여준다. 완료율은 정의된 작업 범위와 집계 기준이 있을 때만 표시한다. 의견 63개가 제출됐다는 사실을 연구가 63% 끝났다는 의미로 바꾸지 않는다.

## 2. 고정된 정보 순서

| 위치 | 내용 | 기본 표시 |
| --- | --- | --- |
| 연구 머리말 | 제목, M1/M2/M3, 현재 작업, 실행 상태, 마지막 갱신 | 항상 |
| 최근 판단 | 핵심 결론, 중요한 한계, 다음 행동 | 짧은 요약 항상 |
| 작업 탐색 | 단계·되돌아간 경로·선택한 작업 | 항상 접근 가능 |
| 선택 작업 | 내용 / 에이전트 대화 / 확인할 문제 / 근거 / 승인·인계 | 공통 탭 구조 |
| 상세 자료 | 전체 후보, 원문, 변경 이력, 실행 정보 | 선택하거나 펼쳐서 |

큰 후보 목록이나 설명문을 작업 탐색 앞에 계속 추가하지 않는다. 새 정보는 위 영역 중 어디에 속하는지 먼저 정한다. 단계별로 독립 페이지를 새로 만들기보다 같은 화면 틀에서 필요한 내용만 바꾼다.

M1은 근거·가설·실험 설계·실행 준비, M2는 실험·결과·다음 방향, M3는 결론·한계·최종 산출물을 중심으로 보여준다. 같은 의미의 대화·근거·쟁점 컴포넌트는 단계가 달라도 동일하게 사용한다.

## 3. 상태를 섞지 않는다

| 구분 | 사용자에게 보여줄 예 | 판단 기준 |
| --- | --- | --- |
| 서버 연결 | 연결됨 / 연결 끊김 | 서버 통신 |
| 실제 실행 | 실행 중 / 입력 대기 / 중단됨 / 이번 작업 종료 / 실행 상태 확인 안 됨 | 실행 기록과 확인 시각 |
| 연구 작업 | 자료 수집 중 / 자료 검토 중 / 가설 검토 중 | 해당 작업 기록 |
| 자료 확인 | 제목 확인 / 초록 확인 / 본문 일부 확인 / 필요한 본문 확인 | 실제 읽은 범위 |
| 자료 사용 판단 | 사용 / 조건부 사용 / 보류 / 제외 | 용도별 검토 결과 |
| 에이전트 의견 | 진행 의견 / 조건부 진행 의견 / 수정 의견 / 보류 의견 | 해당 발언 |
| 단계 완료 | M1 완료 / 완료 조건 미충족 | 정식 단계 평가 |

연결됐다고 에이전트가 일하는 것은 아니다. 의견 작성이 끝났다고 연구가 완료된 것도 아니다. 알 수 없는 상태는 추정해서 채우지 않는다.

실제 수집 작업이 있지만 정식 등록이 아직 없다면 “수집 자료 있음 · 단계 등록 대기”처럼 **두 사실을 함께** 보여준다. 이를 표시하려면 연결된 작업 근거가 있어야 한다. 단순히 단계 상태를 완료로 바꾸지 않는다.

현재 자료와 과거 기록을 같은 현재 시점의 사실처럼 섞지 않는다. 과거 기록을 선택하면 그 시점을 계속 표시하고 최신 요약을 숨기거나 별도임을 명확히 한다.

## 4. 되돌아가는 연구 흐름

작업 지도는 현재 위치와 실제 이력을 보여준다. 문제 발견 → 자료 확인 → 가설 수정 → 재검토 같은 되돌림을 실패로만 표시하지 않는다.

되돌림에는 출발 작업, 돌아간 작업, 이유, 계기가 된 문제·근거, 이후 판단을 연결한다. 계획된 연결과 실제 실행한 연결을 구분한다. 기록이 없는 루프를 그림으로 만들어 실행된 것처럼 보이지 않는다.

시각적 그래프와 같은 내용을 읽을 수 있는 목록을 함께 제공한다. 많은 선으로 전체 기록을 한 번에 펼치기보다 선택한 판단과 관련된 경로를 우선 보여준다.

## 5. 문구 기준

- 첫 문장은 사용자가 알아야 할 사실이나 행동이다. 내부 구현 설명으로 시작하지 않는다.
- 한 문장에 핵심 하나만 담고, 전문어는 필요한 경우에만 뜻을 붙인다.
- 버튼은 결과가 예상되는 동사로 쓴다: “근거 보기”, “이전 판단 보기”, “검토 요청”.
- 수치에는 대상을 붙인다. 중복 제거 기준과 세부 집계 방식은 수치 가까운 설명에서 확인할 수 있게 한다.
- 경고는 문제가 생기는 위치에 둔다. 결론을 바꾸는 한계는 요약에도 남기되 같은 주의사항을 모든 카드에서 반복하지 않는다.
- 오류는 “무슨 일이 생겼는지 → 무엇이 보존됐는지 → 다음 행동”으로 쓴다. 오류 코드는 상세 정보로 둔다.

| 피할 표현 | 권장 표현 |
| --- | --- |
| 최신 탐색 결과를 별도로 표시합니다 | 에이전트가 찾은 논문과 관련 자료입니다 |
| 구조 조건 충족 | 필수 기록 갖춤 — 연구 검증 완료와 구분 |
| blocking_issue_unresolved | 이 단계를 마치려면 확인할 문제가 남아 있습니다 — 해당 문제 연결 |
| 계보 독립성 미확정 | 여러 연구가 같은 데이터를 사용했는지 아직 확인하지 못했습니다 |
| 조건부 진행 | 질문 정리는 계속할 수 있습니다. 학습 전에 측정 단위를 확인해야 합니다 |
| 등록된 작업 없음 | 등록된 작업 없음 — 실제 수행 여부와 구분 |

## 6. 변경 의사결정

새 UI 요청마다 사용자 문제, 들어갈 영역, 사용할 기존 컴포넌트, 상태의 근거, 확인 방법을 짧게 적는다. 기존 규칙으로 해결되면 새 패턴을 만들지 않는다.

규칙을 바꿔야 하면 이유와 영향받는 화면을 기록하고 공통 기준부터 갱신한다. 화면 하나를 위한 CSS·문구 예외를 계속 덧붙이지 않는다. 예외가 필요하면 적용 범위와 재검토 조건을 남긴다.

이 문서는 목표 기준이다. 현재 UI 전체가 이 기준을 충족했다는 선언이 아니다. 미적용 항목은 [적용 목록](review.md)에 관리한다.

## 단계별 피드백과 자율 진행

각 단계의 결론·이유·남은 문제·다음 작업에 피드백을 연결한다. 피드백은 필수 승인이 아니며, 없더라도 허용 범위에서 자율 진행한다. 접수·재검토·반영 여부와 이유를 결론 버전별로 추적한다. 최신 운영 원칙은 [AGENTS.md](../../AGENTS.md)의 단계별 피드백 기준을 따른다. 이 기능의 구현 여부는 별도로 확인한다.
