## Task05 — 신규 프로젝트와 불변 저장

상태: **Task05 완료 · 독립 검토 승인**. 구현 `fe23532`, 검토 보완 `0486946`, 보고서 `45afdf9`. 최종 코드의 별도 프로세스 수용 확인도 통과했다.

사용자가 확인할 결과는 신규 M1 프로젝트를 생성하고 다른 프로세스로 다시 조회해도 동일한 상태가 나오는 것이다. 자료나 결정의 새 버전을 저장해도 이전 버전은 보존되어야 한다.

| 확인 항목 | 기대 동작 | 결과 |
|---|---|---|
| 신규 초기화·다시 열기 | 최초 설정과 같은 HEAD를 읽음 | 별도 CLI 프로세스 확인 통과 |
| 조회 무변경 | 조회 전후 파일 내용·수정 시간이 같음 | 내용·mtime·mode 대조 통과 |
| 기존 프로젝트 분리 | 기존 state.json을 보존하고 M1 초기화 거부 | 공개 CLI에서 양방향 충돌 거부·원본 보존 통과 |
| 명령 재시도 | 같은 명령·같은 내용은 원래 결과, 다른 내용은 충돌 | 원래 HEAD 재시도 수용 확인·내용 충돌 단위 검사 통과 |
| 동시 수정 | 같은 이전 HEAD를 바꾸려는 다른 쓰기는 하나만 성공 | 별도 프로세스 동시 쓰기·동시 초기화 검사 통과 |
| 저장 중 중단 | HEAD는 완전한 이전 또는 새 커밋만 가리킴 | 파일시스템 오류 주입·동기화 실패 재시도 검사 통과 |
| 손상·경로 문제 | 손상된 기록을 복구·정상화하지 않고 오류 표시 | 손상된 HEAD·이력·객체, 심볼릭 링크 거부 검사 통과 |

이 단계는 저장 기반이다. 에이전트 협의, 문헌 승인, 작업 패킷 등록, 실제 기록 UI 연결은 후속 작업이며 여기서 완료로 표시하지 않는다. 실행 확인용 자료는 합성 자료로 구분한다.

기존 전체 회귀 기준선은 Task01에서 SSL 대기로 중단되었다. 이 작업에서는 영향받는 기존 프로젝트·상태·CLI 검사와 신규 저장 검사를 실행하며 전체 회귀 완료와 구분한다.

### 직접 확인하는 명령

개발 작업 공간 `.worktrees/m1-research-graph`에서 **새 경로**를 대상으로 실행한다.

```sh
.venv/bin/researchclaw-codex m1 init ./m1-storage-demo --topic "M1 저장 검사용 합성 프로젝트" --content-origin synthetic --max-returns 2 --json
.venv/bin/researchclaw-codex m1 status ./m1-storage-demo --json
```

`status`는 조회만 수행한다. `m1 resume`이나 노드 등록은 Task06의 범위이며 현재 이 확인 절차에 포함하지 않는다.

별도 프로세스 확인에서는 자료 한 개와 합성 이벤트를 추가한 뒤 명령을 재시도했다. 새 HEAD가 만들어지고, 같은 명령의 재시도 결과가 일치하며, 이전 커밋의 파일 내용과 수정 시간이 보존됨을 확인했다. 이는 저장 API의 확인이며 실제 에이전트 협의 기록이 아니다.

### 독립 검토 보완

초기화의 마지막 디렉터리 동기화가 실패한 뒤 새 명령이 성공을 반환할 수 있는 문제를 독립 검토에서 재현했다. 새 커밋도 저장소의 상위 디렉터리 동기화를 확인한 뒤 성공하도록 수정했다. 실패 지속·동일 명령 재시도·오류 해소 후 성공·더 최신 HEAD 보존을 검사했고, 재검토에서 명세와 품질 모두 승인되었다.

최종 별도 프로세스 확인용 프로젝트는 합성 자료다. 이전 커밋과 새 커밋이 모두 보존되었고, 오류나 성공을 실제 연구 승인으로 사용하지 않았다. 이 단계에서 M1 전체 실행이나 UI 실제 기록 연결을 완료했다고 주장하지 않는다.

## Task06 — 작업 패킷·산출물 등록·재개

상태: **Task06 완료 · 독립 검토 승인**. 구현 `3fcb610`. 최종 코드의 별도 CLI 프로세스 수용 확인도 통과했다.

| 산출물 등록 | 파일 경로·해시·크기를 확인하고 불변 객체로 보존 | 통과 |
| 잘못된 제출 | 외부·미선언 경로와 변경된 입력을 거부 | 통과 |

제출 문서에는 각 논리 파일의 작업 경로·SHA-256·바이트 크기를 넣는다. 실제 허용 목록은 저장된 패킷에서 읽으며 제출자가 임의로 바꾸지 못한다. 합성 자료로 실행 흐름을 확인하고 실제 연구 검토와 구분한다.

### Task06 별도 프로세스 확인

합성 프로젝트에서 scope 패킷을 준비하고 `scope/goal.md`, `scope/constraints.json`을 작성해 등록했다. 등록 뒤 실제 재개 결과는 다음 상태를 보였다.

```json
{"current_node_id":"scope","status":"review_pending","action":"await_review"}
```

대기 이유는 “구조 검사는 끝났으나 독립 검토 또는 협의가 필요함”이다. 이 상태에서 questions 작업을 준비하려는 요청은 거부되었다. 원고 파일을 삭제한 뒤 동일한 제출 문서와 명령 ID로 재시도해도 원래 등록 결과를 반환했다. 반복 재개 조회 전후 파일 내용·mtime·mode는 같았다.

이 확인은 실제 CLI와 저장 API를 사용한 합성 흐름이다. 독립 연구 검토를 수행하거나 승인한 기록은 아니다.

### Task06 검사와 사용 방법

검사 명령: `.venv/bin/python -m pytest tests/codex_native/m1 tests/codex_native/test_task_packets.py -q` — **163 passed**, 실패·건너뜀 없음, 2.72초. 신규 Task06 검사는 32개다. 위 Task05 검사와 중복되므로 합산하지 않는다. 구현 전 실패 확인, 공백 오류 검사, 최종 커밋의 별도 프로세스 확인을 수행했다. 독립 검토는 명세·품질 모두 승인했으며 수정이 필요한 지적은 없었다.

```sh
.venv/bin/researchclaw-codex m1 node prepare ./m1-storage-demo --node scope --command-id prepare-scope-1 --json
.venv/bin/researchclaw-codex m1 node register ./m1-storage-demo --packet PACKET_ID --submission ./submission.json --command-id register-scope-1 --json
.venv/bin/researchclaw-codex m1 resume ./m1-storage-demo --json
```

준비 결과의 `packet.id`를 `PACKET_ID`로 사용한다. 등록 전에 패킷의 필수 파일을 `m1/work/<attempt_id>/` 아래에 작성하고 제출 문서를 만든다. 제출 문서는 `{"schema_version":1,"files":{"scope/goal.md":{"path":"m1/work/<attempt_id>/scope/goal.md","sha256":"<실제 SHA-256>","size":123}}}` 형태이며 모든 필수 파일과 실제 바이트 크기를 포함해야 한다.

위험한 경로·잘못된 제출 형식·해시 불일치는 보정 횟수를 소모하지 않는다. 안전하게 읽은 파일의 내용 형식이 잘못되면 제출 이력과 보정 횟수를 함께 저장한다. 같은 제출의 재시도는 횟수를 추가로 소모하지 않는다.

현재 검사는 파일 구조·구문과 등록 무결성까지다. 과학적 검토는 `not_performed`이며 문헌 승인·내용 검증·협의 엔진은 후속 작업이다. 역할·도구 범위는 패킷에 선언되지만 에이전트 실행 샌드박스를 구현한 것은 아니다. 전체 기존 회귀 검사의 중단 한계도 그대로 남아 있다.
