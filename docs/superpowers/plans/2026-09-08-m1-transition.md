# M1 Research Graph Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 신규 M1 프로젝트에서 자료·가설을 실제 독립 에이전트가 검토하고, 문제에 따라 재탐색·수정하며, 사용자가 근거부터 최종 결정까지 UI로 추적할 수 있게 한다.

**Architecture:** 기존 1~8단계의 자료 검증 기능을 별도 버전의 M1 그래프에서 재사용한다. 원본 단계 상태를 되감지 않고 불변 회차·협의·결정 기록을 새로 연결한다. UI는 그 기록의 읽기 전용 표현이며, 에이전트 실행은 현재 호스트 세션, 승인 기록과 상태 변경은 명시적 CLI 명령이 담당한다.

**Tech Stack:** Python >=3.11, 기존 argparse·pytest·PyYAML과 경로/원자적 저장 도구. UI 초안은 HTML/CSS/JavaScript와 고정 JSON 계약을 사용한다. 새 프런트엔드 프레임워크·외부 LLM 런타임·그래프 DB는 도입하지 않는다. 실제 UI 제작 시 제공되는 Sites 스킬의 프로젝트·호스팅 규칙을 먼저 확인하며, 연구 데이터의 외부 배포는 이 계획에 포함하지 않는다.

**Spec:** [세 마일스톤 그래프](../specs/2026-09-08-three-milestone-research-graph-design.md), M1에 한정. 이후 사용자 보완: 가설 생성 뒤 독립 검토·수정 루프가 필요하며, M1에서도 개략적 검증 가능성을 다룬다. M2의 상세 설계·실행은 수행하지 않는다.

## 계획의 상태와 읽는 법

2026-09-08 코드 검토를 기준으로 만든 **사용자 검토용 수정 계획**이다. 사용자의 시작 요청에 따라 별도 작업 공간에서 A 묶음 구현을 시작했다. 진행 상황은 [실행 현황](2026-09-08-m1-progress.md)에 기록한다. 아래 M1 신규 정책은 제안된 기본값이며 기존 프로젝트 규칙으로 소급 적용하지 않는다. 첫 작업 01에서 확인할 결정 목록을 제시한다.

사용자는 이 문서의 20개 작업과 다섯 확인 지점만 읽어도 진행 여부를 판단할 수 있다. 구현자는 해당 하위 계획과 이 문서의 공통 계약을 함께 읽는다. 각 작업은 별도 검토·커밋 가능한 단위이며 내부에는 짧은 실행 체크리스트가 있다.

## Global Constraints

- Python >=3.11. 현재 기본 Python은 3.9.6이며 pytest가 없어 테스트 기준 환경부터 준비한다. 설치된 다른 Python이 있는지 먼저 확인한다.
- "기존 프로젝트의 상태·승인·증거·규칙은 유지한다. 새로운 그래프는 별도 워크플로 버전으로 개발한다."
- "조정자는 타인의 발언·최종 의견·합의를 작성하지 않는다."
- "기본 응답 라운드는 한 차례다. 추가 협의는 새 근거·새 질문·허용 예산이 있을 때만 새 회차로 기록한다."
- "인용 검증은 M1부터 반복하고 M3 최종 패키지의 선행 조건으로 둔다. 기록 보존은 매 노드에서 수행하며 M3의 최종 보관으로 대체하지 않는다."
- M1만 구현한다. M2·M3, 실험 실행, 기존 프로젝트 자동 이전, 원본 autonomous 실행기 전환은 제외한다.
- Python 엔진은 외부 LLM API 키를 받거나 에이전트 프로세스를 실행하지 않는다. 현재 호스트의 실제 에이전트와 허용 도구를 사용한다.
- 자료·원문·등록 JSON은 신뢰할 수 없는 입력이다. 그 안의 명령을 실행하지 않고 UI에서도 HTML로 해석하지 않는다.
- 문헌 승인 권한은 사용자에게 있다. 새로운 문헌 집합은 새 승인 대상이며 과거 승인은 보존한다.
- 역할 표시, 모델 이름, 제출자 문자열만으로 독립 실행이 입증됐다고 표시하지 않는다.
- 구조 검사와 과학적 타당성 검토를 분리한다. 성공 시나리오뿐 아니라 유보·기각·실패도 정상적인 연구 결과로 보여준다.
- 임의의 개선·가설·반론 개수를 채우지 않는다. 신규 M1에 기존 '2~5개 후보·숫자 예측·반대 가설 필수' 규칙을 무조건 이식하지 않는다.
- JSON CLI 성공은 stdout 한 값, 오류는 stderr와 exit 2. 읽기 전용 조회는 정상화·등록·진행 변경을 하지 않는다.
- 각 묶음에서 확인 결과를 보고하되 이미 허용된 작업마다 형식적인 재승인을 요구하지 않는다. 사용자 선택이 필요한 정책 변경과 실패는 구분해 보고한다.
- 이 계획 경로는 현재 `.gitignore`의 `docs/superpowers/`에 포함된다. 파일은 로컬에 저장되지만 일반 `git add`로 추적되지 않는다. 추적 시 문서의 공개 적합성을 확인하고 해당 파일만 명시적으로 추가한다. 전체 ignore 규칙을 풀지 않는다.

## 4. 신규 M1 공통 계약 — 제안 기본값

### 작업 노드

`scope → questions → search → collect → screen → extract → synthesize → hypothesize → review → handoff`.

앞의 일곱 노드에서도 필요한 협의/독립 확인을 완료해야 진행한다(작업 17에서 통합). `hypothesize`는 작성, `review`는 독립 심사로 분리한다. `screen` 뒤에는 사용자 문헌 승인이 필요하다.

`review`의 복귀 목적지는 `scope`, `questions`, `search`, `collect`, `screen`, `extract`, `synthesize`, `hypothesize`다. 이유 코드와 영향 목록이 있어야 하며 앞 번호라는 이유만으로 모든 결과를 지우지 않는다. 새 자료가 선택 문헌 집합을 바꾸면 `screen` 승인을 다시 거친다.

앞 단계 협의·독립 확인에도 복귀가 필요하다. 노드별 허용 목적지는 A 작업 04의 RETURN_TARGETS로 정한다. 같은 노드의 초안 보정과 이미 등록된 결과의 재검토를 구분한다. 초안 보정도 이력을 남기지만 추가 복귀 예산은 등록된 결정으로 새 회차를 시작할 때만 차감한다. 검사 오류만으로 무제한 재시도하지 않도록 패킷별 초안 수정 한도 기본값은 2회로 제안하며, 소진 시 사용자 판단 대기로 둔다. task01 정책 확인에 포함하고 task06/14에서 적용·검사한다.

### 프로젝트·저장

- 새 명령 묶음 `researchclaw-codex m1 ...`만 신규 흐름을 연다. 기존 `init/status/resume/stage`는 유지한다.
- 새 루트에는 `.researchclaw/m1/`를 생성하며 기존 `.researchclaw/state.json`과 공존시키지 않는다. 기존 루트를 M1으로 여는 요청은 `m1_legacy_project_requires_explicit_migration`으로 거부한다. 자동 migration 명령은 만들지 않는다.
- `workflow_version="m1-graph-v1"`, 문서·조회 JSON `schema_version=1`.
- `.researchclaw/m1/commits/<id>/`에 완전한 상태·이벤트·참조 목록을 저장하고 검증 후 `HEAD.json`을 원자적으로 교체한다. 객체는 SHA-256로 참조하며 등록 후 변경하지 않는다. UI는 HEAD로 연결된 커밋만 읽는다.
- 승인·협의·회차도 같은 커밋 경계에 포함한다. 별도 이벤트 로그와 상태 파일을 독립 갱신해 반쪽 성공을 만들지 않는다.
- 작업 원고는 패킷이 선언한 `m1/work/<attempt_id>/...`에 작성한다. 엔진만 불변 객체·완료 참조를 발행한다. 객체 보존을 악성 소유자에 대한 완전한 방어로 과장하지 않는다.

### 핵심 레코드

| 레코드 | 필수 필드 |
| --- | --- |
| NodeAttempt | `id,node_id,revision,parent_attempt_id,input_refs,status,output_refs` |
| ArtifactRef | `id,logical_path,sha256,size,producer_attempt_id` |
| Assignment | `id,session_id,role_id,host_task_id,provenance_status,input_binding,allowed_outputs` |
| Issue | `id,session_id,raised_by,target_refs,question,evidence_refs,impact,severity,resolution_condition` |
| Response | `id,issue_id,assignment_id,stance,rationale,evidence_refs` |
| FinalPosition | `assignment_id,input_binding,recommendation,issue_dispositions,rationale,evidence_refs` |
| Decision | `id,session_id,input_binding,positions,selected_hypothesis_ids,dissent,limitations,next_action` |
| TransitionPlan | `from_attempt_id,target_node_id,reason_code,issue_ids,affected_attempt_ids,approval_effects` |

`input_binding`는 검토 대상 산출물의 정렬된 ID·해시와 패킷 버전의 결합이다. 문자열 판단 이유는 비어 있으면 거부한다. 근거 참조는 같은 프로젝트의 등록 객체로 해석돼야 한다. 사실 확인에 외부 자료를 추가해야 하면 자료 작업으로 돌리고 새 입력 결합을 만든다.

### 가설·협의·반복 정책

- 가설 ID와 revision은 분리한다. M1 레코드는 `statement,claim_refs,gap_refs,predicted_observation,falsification_condition,alternatives,feasibility_notes,open_design_questions,disposition`을 가진다. 수치가 아직 정당화되지 않았다면 숫자를 만들어 넣지 않는다.
- 후보가 없으면 '가설 없음'과 이유를 기록할 수 있으나 완료 인계는 불가하다. 근거 있는 후보 하나는 허용한다. 단순히 주류에 반대하는 후보를 의무 생성하지 않는다.
- `disposition`: `draft`, `revise`, `selected`, `rejected`, `deferred`. 'selected'는 가설의 참을 의미하지 않는다.
- 세 판단 역할은 `domain`, `methodology`, `critical_reproducibility`. `coordinator`는 비투표, 작성자는 자기 산출물의 독립 심사자로 배정하지 않는다.
- 초기 세 제출 전 타인의 초기 의견을 패킷에 포함하지 않는다. 이후 한 차례 응답과 각자의 최종 입장을 요구한다.
- 제안 진행 조건: 세 필수 최종 입장이 모두 `ready` 또는 `ready_with_limits`, 차단 쟁점 모두 해소, 선택 가설이 하나 이상, 필요한 사용자 승인이 현재 입력과 일치. 한 역할이 `revise` 또는 `defer`면 조정자가 임의로 진행하지 않는다.
- `ready_with_limits`는 이견 보존을 허용하나 실제 차단 문제를 문구만 바꿔 숨기지 않는다. 차단 해소는 제기자의 확인 또는 새 독립 재검토 기록을 필요로 한다.
- 기본 한 응답 라운드. 신규 프로젝트의 최초 반복 예산 제안은 **추가 복귀 2회**로 명시하며 UI에 표시한다. 사용자가 다른 예산을 정할 수 있고 자동 증액하지 않는다. 시간·자료 접근 상한이 먼저 도달하면 대기한다. 두 회차가 연구 품질 기준은 아니다.
- 입력도 쟁점도 달라지지 않은 동일 재논의는 `m1_no_new_basis`로 거부한다. 새 회차는 근거/가설 변경 또는 승인된 미해결 질문·추가 작업을 참조한다.

### UI와 실행 경계

첫 UI는 읽기 전용이다. 그래프 선택·쟁점 탐색·버전 비교는 가능하지만 승인/에이전트 실행 버튼은 만들지 않는다. 사용자는 대화에서 승인하고 CLI가 기록한다. 승인 화면까지 동시에 개발해 핵심 이력 확인을 지연시키지 않는다.

공통 조회 형태는 `schema_version,workflow_version,data_origin,project,nodes,edges,attempts,artifacts,sessions,issues,responses,decisions,approvals,next_actions`다. `data_origin`은 `demo` 또는 `registered`; 시안에 실제 연구 완료 배지를 붙이지 않는다.

`project.content_origin`은 `synthetic` 또는 `research`로 구분한다. 실제 에이전트가 합성 자료를 검토한 경우도 자료는 synthetic이다. 등록된 기록이라는 표시, 실제 배정 출처 수준, 자료의 합성 여부를 서로 혼동하지 않는다.

처음에는 JSON 파일로 시안을 검증한다. 작업 16에서 `m1 view ROOT`의 로컬 읽기 전용 제공 경로와 연결한다. 서버는 loopback에만 바인딩하고 지정 프로젝트의 등록 자료만 노출한다. 변경·실행 API, 외부 호스팅, 임의 파일 탐색은 없다.

## 6. 각 작업의 공통 실행·보고 순서

- [ ] 구현용 격리 작업공간과 적용 지침을 확인한다. 사용자 작업·기존 연구 프로젝트를 보존한다.
- [ ] 해당 작업의 실제 실패/오용 사례를 검증하는 테스트를 추가하고, 기능 부재 때문에 실패함을 확인한다.
- [ ] 명시된 파일 책임 안에서 구현한다. 예상 밖 정책 변경은 계획에 기록하고 판단을 받는다.
- [ ] 해당 검사와 영향받는 기존 검사를 실행한다. 테스트 수·실패·건너뜀을 구분한다.
- [ ] 사용자가 확인할 화면 또는 CLI·기록 사례, 알려진 제한, 다음 작업을 보고한다.
- [ ] 검토된 파일만 작업 커밋으로 묶는다. 이 계획 작성 턴에는 코드 변경·커밋·푸시·설치 갱신을 하지 않는다.

전체 기본 회귀는 기준선과 통합 완료 시 실행한다. 매 작은 변경마다 전체 검사를 반복하지 않는다. 테스트 예시에서 `fixture`는 실제 독립 에이전트 수행의 증거가 아니며 작업 03·17·20의 실제 수행 기록과 별도로 보고한다.

## 7. M1 완료 판단 체크리스트

- [ ] 자료와 가설을 만드는 전체 경로 및 독립 검토가 연결됨.
- [ ] 자료 부족·가설 문제·해석 문제에 따라 정확한 노드로 돌아감.
- [ ] 왜 방향을 선택·수정·기각했는지 실제 발언과 근거로 추적됨.
- [ ] 예시 데이터·등록 기록·독립 실행 확인 수준이 UI에서 구분됨.
- [ ] 문헌 변경과 가설 변경이 필요한 승인·재검토에 반영됨.
- [ ] 중단·재개·중복 등록·예산 소진이 기록을 훼손하지 않음.
- [ ] M1 인계는 구체적 실험 실행이나 M2 자동 시작을 하지 않음.
- [ ] 기존 1~15단계 및 설치 패키지 회귀 확인.
- [ ] 실제 사용자 검토 사례에서 결정 이유를 찾을 수 있음.

## 8. 확인 결과 기록 형식

각 작업 결과는 해당 묶음의 검증 문서에 다음 표로 남긴다.

| 항목 | 기록 내용 |
| --- | --- |
| 작업·커밋·환경 | ID, 변경 커밋, Python/브라우저, 실행 위치 |
| 변경 내용 | 사용자에게 생긴 기능과 적용 범위 |
| 증거 | 검사 명령·결과, 실제 프로젝트/회차/쟁점 식별자 |
| 사용자 확인 | 열어 볼 경로와 기대되는 행동 |
| 제한 | 미구현·미확인·호스트에서 보장되지 않는 사항 |
| 다음 작업 | 선행 조건 충족 여부와 남은 결정 |

첫 시작점은 01이다. 화면은 02에서 먼저 보고, 실제 협의는 03에서 호스트 가능성을 확인한 뒤 10~12에서 정식 기록에 연결한다.
