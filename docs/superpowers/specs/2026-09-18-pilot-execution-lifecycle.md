# Pilot 연구 실행·기록·UI 공통 설계

상태: 사용자와 합의한 방향을 구현 계약으로 구체화. 구현·운영 반영 완료 아님.
근거: [통합 감사](../../audits/2026-09-18-research-execution/README.md), [외부 인터페이스 감사](../../audits/2026-09-18-research-execution/documents-atlas-interface.md), AGENTS.md.

## 1. 범위와 원칙

Pilot은 승인된 현재 마일스톤까지 연구를 조정한다. 단계 종류와 실제 수행 순서는 분리한다. 필수 작업은 검사 없이 생략할 수 없고, 해당하지 않는 조건은 적용 제외 이유·영향·판정자를 남긴다. 사용자의 무응답을 승인으로 만들지 않는다. 탐색/초안마다 다중 토론을 강제하지 않으며 중요한 판단과 마일스톤 종료에 필요한 검토를 적용한다.

기존 연구·원형·대화·외부 영수증을 보존한다. 기존 API 계약과 인증을 유지한다. 새 구현을 보관된 실제 연구에 자동 적용하거나 완료 상태를 소급 생성하지 않는다. 새 격리 프로젝트에서 수락한 뒤 명시적으로 운영 연결한다.

## 2. 공통 단계 계약

계약 version 1은 `step_id`, `purpose_kind`(research/assessment/planning), `purpose`, `milestone`, `required_inputs`, `roles`, `output_schema`, `acceptance_checks`, `dependencies`, `allowed_successors`를 갖는다. 역할에는 persona 목적·모델 프로필 snapshot·요청 추론 설정·확인된 실제 설정을 구분해 기록한다. 입력은 로컬 불변 object hash 또는 검증된 외부 result_ref로 고정한다.

각 수행은 `work_id`, `attempt_id`, `contract_ref`, `input_revision`, `policy_revision`, `assignment_revision`, `generation`, `return_from`을 갖는다. 단계 ID는 이름 변경에도 유지한다. 같은 단계 재수행은 새 attempt로 연결하며 이전 발언과 실패를 덮어쓰지 않는다.

시작 검사는 필수 입력 접근·hash, 목적/권한, 담당 역할, 모델 설정의 지원 여부, 선행 조건을 판정한다. 종료 검사는 출력 schema/원형·근거 위치·필수 검토·현재 입력 적합성을 판정한다. 과학적 의미 검토는 별도의 실제 검토 산출물로 제공한다. 구조 검사를 과학적 타당성 보증으로 표시하지 않는다.

판정은 `pass`, `needs_work`, `blocked`, `not_applicable`이다. 각 항목은 check_id/checker_version/근거 참조/이유/영향받는 판단/다음 행동을 기록한다. not_applicable에는 계약이 허용하는 적용 제외 조건이 필요하다. 임의 문자열 done은 판정 근거가 아니다.

## 3. 상태·훅·종료의 의미

작업 상태: `planned → checking_input → running / waiting_input / blocked → checking_output → accepted / needs_work / blocked`.
기술 실패는 `failed`, 사용자 일시정지는 `paused`, 미확정 실행 복구는 `recovery_required`로 구분한다. 이는 설계상의 상태명이며 기존 서비스 enum을 바꾸라는 요구가 아니다.

시작 훅은 입력 검사를 기록한 뒤 실행을 허용한다. 종료 훅은 저장된 결과를 검사하고, 입력·정책·배정 revision과 generation을 commit 직전에 다시 확인한다. 오래된 결과는 저장하되 채택하지 않는다. 훅 자체 오류도 실패 이벤트로 남긴다. 초안 저장과 채택은 다른 권한이다.

`작업 실행 종료`, `검토 완료`, `판단 채택`, `마일스톤 완료`, `다음 마일스톤 인계 수락`을 구분한다. episode.conclude/policy completed만으로 새 실행 체계의 accepted나 milestone complete를 만들 수 없다. 기존 native gate/handoff를 목적에 맞게 연결하고, 맞지 않는 schema에 가짜 입력을 채우지 않는다.

## 4. 공통 이벤트와 UI

기존 graph commit/CAS/멱등 command_id를 재사용한다. 논리 이벤트는 schema_version/project_id/work_id/attempt_id/step_id/event_id/sequence/occurred_at/type/actor/input_revision/causation_id/payload를 갖는다. sequence는 프로젝트 commit 순서이며 원격 시각으로 정렬하지 않는다. payload는 검증된 공개 요약과 불변 artifact 참조로 분리한다. 인증·개인 경로·비공개 내부 추론은 공개하지 않는다.

필수 이벤트: 계약 고정, 입력 검사, 역할 실행 시작/진행/종료, 도구 요청/접수/대기/수신, 발언 제출/공개, 출력 검사, 채택/보류, 재작업 배정, 정지/재개, 마일스톤 검사. 동일 event_id 재전송은 하나로 보이고 내용 충돌은 거부한다.

UI는 같은 이벤트를 투영한다. 하단부터 수행 순서가 쌓이고 새 수행은 위에 나타난다. 접힌 행에는 단계·현재 상태·현재 할 일/대기 이유, 펼친 영역에는 요약 / 대화 / 도구 / 검사·재작업 / 결과·근거를 제공한다. 처음 의견→상호 검토→최종 판단은 탭으로, 발언은 요약+원문 펼침으로 보인다.

독립 첫 의견 작성 중 사용자에게 역할별 진행은 보이되 동료 입력으로는 비공개를 유지한다. 내용은 공개 장벽을 충족한 뒤 표시한다. 제출 원문과 조정자 요약은 별도 표시한다. 과거 HEAD에서는 미래 이벤트를 섞지 않는다.

연결 성공과 워커 생존을 구분한다. 영속 이벤트는 정상 로컬 연결에서 5초 안에 표시하는 것을 첫 UI 수락 목표로 한다. 장시간 모델 작업은 15초 간격 생존 기록, 45초 이상 미관측이면 ‘실행 상태 확인 필요’로 표시한다. 이 값은 연구 중단 제한이 아니며 미관측만으로 실패/재실행하지 않는다. 스크롤·선택·펼침·입력 중 내용은 갱신/재접속 중 보존한다.

## 5. 재작업·되돌림·재개

needs_work는 실패 기준/보완 작업/입력/담당/종료 조건을 연결한 새 attempt를 만든다. 단계 되돌림은 영향받는 채택 결과를 재검토 상태로 연결하고 원래 결과를 보존한다. 의존하지 않는 작업은 계속한다. 새 근거나 접근 변경이 없는 반복은 공백과 다음 필요조건을 명시해 해당 판단을 보류한다. 횟수 소진으로 강제 통과하지 않는다.

재개는 저장 원장에서 요청 의도·접수 영수증·결과 수신·검토 산출물·채택 기록을 대조한다. 이미 완료된 모델 결과는 재사용하고 실행 여부 불명확한 작업은 recovery_required로 둔다. 원격 취소와 로컬 배정 중지는 별개다. 중단된 프로젝트에 도착한 결과는 보존하되 새 작업을 시작하지 않는다. 외부 실행의 exactly-once를 보장한다고 주장하지 않는다.

## 6. Documents·Atlas 연결

Pilot→Documents 접수, Atlas import 의뢰, Atlas의 Documents 회수/지식화, Pilot 이벤트 수신/ACK 계약을 유지한다. A1 질의와 E 복합 지식 반영은 각 인증·capability·결과 의미를 유지하며 별도 adapter로 공통 work에 연결한다.

원격 task/import/job, receipt/result_ref를 원래 work/attempt/role/input_revision에 연결한다. ACK는 원형 수신 후 가능하지만 검토 완료와 다르다. partial은 기술 결함과 근거 공백을 구분한 뒤 사용 가능한 범위를 검토한다. 실패 result_ref만으로 과학 토론을 시작하지 않는다. 공통 consumer의 타 프로젝트 이벤트도 보존·분배 가능해야 하며 매칭 실패는 미배정으로 기록한다.

## 7. M1 전체 적용표

| 단계 종류 | 필수 결과 | 부족할 때 |
| --- | --- | --- |
| 범위·질문 | 원 요청과 일치하는 목적/비교/범위/종료 기준 | 영향이 큰 모호함 보완 |
| 검색·수집 | 서지·버전·확보 여부·읽을 범위 | 대체 출처/사용자 원문/한계 처리 |
| 변환·지식화 | 검증된 결과 참조·읽은 범위·partial 사유 | 기술 복구 또는 자료 보완 |
| 근거 검토 | 주장 지지 범위·반례·사용/한정/보류 | 추가 질의/자료/해석 수정 |
| 종합·가설 | 경쟁 설명·예측·반증 조건·논의된 판단 | 근거 또는 가설 재검토 |
| 설계·준비 | 목적별 실행/작성 계획·검수·실패 처리·표준 산출물 | 설계 보완/전제 재검토 |
| 최종 검토·인계 | 필수 결과 버전과 검사·미정 항목 처리·인계 패키지 | 영향 작업 재개; M1 완료 보류 |

조사/계획 목적에는 불필요한 실험을 강제하지 않는다. 최종 산출물은 versioned JSON을 기준으로 Markdown을 생성하고 Presentation 패키지의 주장과 근거를 연결한다.

## 8. 분할 구현과 수락

첫 단위는 ‘보관된 Atlas 근거 한 건의 검토’다. 격리 합성 입력으로 시작 검사→역할 실행/발언→필수 근거 누락으로 종료 거부→보완→재개→사용 범위 채택을 UI까지 검증한다. 이 단위는 M1 완료가 아니다. 별도 소규모 실제 모델 시험으로 발언/근거 품질을 확인한다.

후속은 외부 전송 연결, 영향/후속 스케줄링, M1 전 단계·목적별 gate, 모델 설정·산출물, 전체 종단 수락 순서다. 감사 G01–G16 및 DOC-01–30은 추적표에서 담당 구현 단위와 수락 증거가 생겨야 닫는다. 첫 단위 성공을 나머지 항목 완료로 확장하지 않는다.
