# M1 범위·진행 정책 계약 v1

작성일: 2026-09-08 (Asia/Seoul)

상태: M1 구현을 시작하기 위한 신규 프로젝트용 v1 기본값. 사용자가 총괄 계획 시작을 허용한 범위에서 채택한 되돌릴 수 있는 개발 기본값이며, 특정 연구의 문헌·방향·예산·결과 승인이 아니다.

## 적용 범위

M1은 `workflow_version="m1-graph-v1"`인 새 프로젝트만 지원하도록 구현한다. 향후 작업에서 새 명령 묶음 `researchclaw-codex m1 ...`이 `.researchclaw/m1/` 저장소를 만들고 사용하게 된다. Task 01 시점에는 이 명령과 저장소가 아직 구현되지 않았다. 기존 `init/status/resume/stage` 흐름, `.researchclaw/state.json`, 과거 승인·증거·완료 판정은 그대로 유지한다.

기존 ResearchClaw 루트를 M1으로 여는 요청은 `m1_legacy_project_requires_explicit_migration`으로 거부한다. v1은 자동 이전 명령을 제공하지 않으며, 기존 저장소와 M1 저장소를 같은 프로젝트 루트에 공존시키지 않는다. 검증기나 증거 보존 도구를 재사용할 때도 기존 레코드의 의미를 바꾸지 않는다.

## 판단 역할과 진행 조건

판단 협의에는 서로 구분된 세 역할이 필요하다.

| 역할 | 판단 책임 |
| --- | --- |
| `domain` | 연구 맥락, 현상의 의미, 기여와 경쟁 방향 |
| `methodology` | 비교 가능성, 검증 가능성, 방법상의 한계 |
| `critical_reproducibility` | 원문 대조, 선택 편향, 반대 설명, 재현 가능성 |

`coordinator`는 쟁점과 기록을 정리하지만 투표하지 않고, 다른 역할의 발언·최종 의견·합의를 대신 작성하지 않는다. 작성자는 자기 산출물의 독립 심사자로 배정될 수 없다. 역할명, 모델명, 제출자 문자열만으로 독립 실행이 증명되지는 않는다.

판단 협의를 마치고 다음 노드로 진행하려면 다음 공통 조건을 충족해야 한다.

1. 세 필수 역할이 현재 `input_binding`에 결합된 최종 입장을 모두 제출한다.
2. 각 최종 입장이 `ready` 또는 `ready_with_limits`다.
3. 차단 쟁점이 모두 해소됐다. 해소는 쟁점 제기자의 확인이나 새 독립 재검토 기록으로 남긴다.
4. 해당 노드가 요구하는 산출물이 등록됐고, 필요한 사용자 승인이 현재 입력 버전과 일치한다.

`review` 완료와 M1 `handoff`에는 선택 가설이 하나 이상이어야 한다. `scope`, `questions`, `search` 등 앞 노드에는 아직 존재하지 않는 선택 가설을 요구하지 않고, 각 노드의 산출물·승인·차단 쟁점 기준을 적용한다. 앞 단계의 구체적인 역할과 완료 조건은 Task 04와 Task 17에서 노드별로 고정한다.

`ready_with_limits`는 남은 이견과 한계를 보존하는 상태다. 차단 문제를 표현만 완화해 통과시키는 수단이 아니다. 한 역할이라도 `revise` 또는 `defer`이면 조정자가 다수결로 진행시킬 수 없다. 제출이 없거나 역할 실행을 확인할 수 없는 경우도 동의로 간주하지 않는다.

예를 들어 `review`에서 분야 역할이 `ready`, 방법론 역할이 `ready_with_limits`를 제출했더라도 비판·재현성 역할이 “핵심 수치가 원문과 대조되지 않았다”는 차단 쟁점과 함께 `revise`를 제출하면 2 대 1로 통과하지 않는다. `extract` 또는 필요한 자료 노드로 돌아가 원문 위치와 추출을 새 버전으로 등록하고, 쟁점 제기자가 해소를 확인하거나 새 독립 재검토가 이를 확인한 뒤 세 역할이 새 입력에 최종 입장을 제출해야 진행할 수 있다.

## 응답 라운드와 복귀 예산

한 협의 회차의 기본 순서는 입력·질문·버전 고정, 세 역할의 비공개 독립 제출, 전체 제출 후 공개, 쟁점별 응답 한 차례, 역할별 최종 입장, 결정 기록이다. “한 응답 라운드”는 최초 제출 공개 뒤 각 역할이 현재 쟁점에 응답할 기회가 한 번 있다는 뜻이다. 논의량을 채우기 위해 반론을 만들거나 같은 입력과 쟁점으로 응답을 무한 반복하지 않는다.

추가 협의는 새 근거, 변경된 가설, 새 질문, 또는 승인된 미해결 질문·추가 작업이 있을 때 새 회차로 기록한다. 입력과 쟁점이 달라지지 않은 재논의는 `m1_no_new_basis`로 거부한다.

신규 프로젝트의 v1 기본 추가 복귀 예산은 2회다. 이는 정상적인 최초 전진 경로 뒤, 등록된 결정으로 과거 작업 노드에 돌아가 새 `NodeAttempt`를 시작할 수 있는 횟수다. 같은 패킷의 등록 전 초안 보정은 복귀 예산을 소모하지 않는다. 패킷별 초안 수정 한도는 별도의 v1 기본값 2회이며, 소진하면 사용자 판단을 기다린다.

두 번의 복귀는 연구 품질 기준이나 반드시 사용해야 하는 목표가 아니다. 시간·자료 접근 한도가 먼저 끝나거나 추가 작업 권한이 없으면 상태를 보존하고 대기한다. 엔진은 예산을 자동으로 늘리지 않는다. 사용자는 신규 프로젝트 설정이나 명시적인 후속 결정으로 다른 값을 정할 수 있으며, 그 값과 적용 시점을 기록한다. 이 문서의 기본값이나 일반 대화에서 추측한 수치를 특정 연구의 승인된 예산으로 기록하지 않는다.

## 첫 UI와 승인 경계

첫 UI는 등록 또는 예시 JSON의 읽기 전용 표현이다. 사용자는 그래프 노드, 쟁점, 응답, 결정 계보와 가설 버전을 선택하고 비교할 수 있다. UI에는 승인, 에이전트 실행, 상태 변경 버튼이나 쓰기 API를 두지 않는다. 연구 텍스트는 신뢰할 수 없는 입력으로 취급하며 HTML로 실행하지 않는다.

사용자는 현재 호스트 대화에서 결정을 내리고, CLI가 그 결정을 현재 입력 버전에 결합해 기록한다. UI에서 탐색하거나 화면을 열었다는 사실은 승인이 아니다. 작업 16에서 실제 기록을 연결할 때도 로컬 loopback 읽기 전용 경로만 제공하며 외부 호스팅이나 임의 파일 탐색은 v1 범위에 포함하지 않는다.

## 검토 결과와 변경 방법

| 정책 | Task 01 결과 | 변경이 필요할 때 |
| --- | --- | --- |
| 신규 프로젝트만 지원 | v1 기본값으로 채택 | 별도 이전 설계와 사용자 결정을 새 작업으로 기록 |
| 세 역할 전원 진행 가능 + 차단 쟁점 해소 | v1 기본값으로 채택 | 역할·정족수 변경의 영향과 실패 사례를 먼저 검토 |
| 응답 1회, 추가 복귀 2회 | v1 기본값으로 채택 | 프로젝트별 명시 설정 또는 기록된 후속 사용자 결정 |
| UI 읽기 전용, 대화 결정 + CLI 기록 | v1 기본값으로 채택 | 쓰기 UI의 권한·입력 결합·실패 복구를 별도 설계 |

이 네 항목은 구현 계약을 시작하기 위한 정책 검토 결과다. 문헌 집합 승인, 연구 가설 채택, 추가 작업 허가, 개별 프로젝트 예산 승인으로 재사용할 수 없다.
