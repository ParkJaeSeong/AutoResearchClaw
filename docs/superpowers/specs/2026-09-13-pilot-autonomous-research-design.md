# Pilot 자율 연구 과정·UI·자료 수집 설계 정리

상태: 브레인스토밍 통합 검토본. 합의한 방향을 정리한 문서이며 구현 명세 확정·개발 완료·연구 완료를 뜻하지 않는다. 2026-09-13 사용자 대화를 기준으로 작성했다.

## 1. 목적과 범위

사용자는 결과뿐 아니라 에이전트가 어떻게 자율 연구를 수행했는지 보고 싶다. 어떤 질문으로 작업을 시작했고, 무엇을 찾고, 어떻게 반박·검토했으며, 어떤 도구 결과를 사용해 다음 행동을 선택했는지 추적한다.

현재 우선순위는 좋은 실험 계획을 세우는 M1이다. 실험 연구에서 Pilot은 근거·가설·실험 설계·착수 준비에 집중한다. M1 완료와 M2 실행 시작은 분리한다. 셀프드라이빙랩은 별도 에이전트/시스템으로 설계한다. Pilot은 연구 목적·주요 조건을 정하고 실행 담당은 실행 가능성과 수행 방법을 검토한다. 목적·주요 조건 변경은 다시 협의한다. 장비 연결·실행 권한·중단·재개 등 상세 계약은 이번 설계 밖이다.

문헌만으로 끝나는 연구는 Pilot이 근거 종합·결론 검토·최종 산출물까지 책임진다. 이 연구 유형의 마일스톤 구성은 후속 설계 대상으로, 실험 없는 연구에 형식적인 실험 준비 단계를 강제하지 않는다.

기존 프로젝트 전체 삭제는 합의하지 않았다. 기존 연구 원문·판단 이력·Atlas 계약은 보존을 전제로 검토하며, 새 구조로 이전하는 방법은 별도 결정한다.

## 2. 단계와 수행 순서 분리

단계는 작업의 종류이고 순서는 실제 실행 이력이다. 현재 정리한 M1 단계는 범위 설정 → 질문 구체화 → 자료 탐색 → 자료 선정 → 원문 확보 → 근거 추출·분석 → 근거 종합 → 가설 수립·검토 → 실험 설계·착수 준비 → 최종 검토·인계이다. 이 이름과 묶음은 설계상 분류이며 기존 런타임 노드가 그대로 구현됐다는 뜻은 아니다.

예: 003 문헌 탐색 → 004 근거 분석 → 005 가설 검토 → 006 문헌 추가 탐색 → 007 근거 재분석. 추가 탐색은 과거 카드를 덮어쓰지 않는다. 이전 작업과 되돌아온 이유·영향 범위를 연결한다. 순서만으로 작업 간 의존성을 추정하지 않는다.

## 3. 공통 작업 카드와 UI

작업 카드는 하나의 목적을 가진 수행 회차이다. 새 질문이나 재검토 목적이 생기면 새 카드로 만들고, 같은 작업의 발언·도구 호출·재시도는 그 안에 쌓는다.

아래가 과거, 위가 최신이다. 시작 순서로 카드 위치를 고정하고 완료 시 재정렬하지 않는다. 병렬 작업은 각 상태와 의존성을 표시한다. 과거 내용을 읽는 중에는 새 작업으로 화면을 밀지 않고 알림을 제공하는 방안을 제안했다.

공통 상세 구조:
1. 요약: 목적·결과·남은 문제·다음 작업과 선택 이유.
2. 진행 과정: 에이전트 의견 → 도구 요청 → 반환 근거 → 반박·재검토 → 판단을 실제 순서로 연결. 대화만/도구만 보기 지원 방향.
3. 산출물: 결과 문서·자료·근거와 원문 연결.

도구 기록은 호출 주체, 목적, 요청, 상태, 응답, 오류·재시도, 활용한 판단을 연결한다. Documents를 Atlas가 호출했다면 Atlas 하위 기록으로 표시한다. 전달받지 못한 하위 기록이나 실제로 하지 않은 호출은 만들지 않는다. 원래 발언과 조정자의 요약을 구분한다.

작업 상태와 연구 판단을 분리한다. 예: 작업 종료 / 판단 보류 / 개발 검토 대기. 작업 종료가 단계 또는 마일스톤 완료를 뜻하지 않는다. 부분 결과가 있는 도구 실패와 연구 근거 부족도 구분한다. 정확한 상태 전이표는 구현 전 설계한다.

마일스톤 완료 시 결과 카드를 위에 두고 지난 과정은 접어 보존한다. 결과에서 관련 작업·대화·근거로 이동할 수 있다. M1 결과는 질문·가설·실험 계획·착수 준비·남은 문제·인계 사항을 포함한다. 나중에 재검토하면 기존 결과를 보존하고 새 작업과 연결한다.

Presentation 기반 색상·서체·간격 등 공통 시각 규칙은 유지한다. 최신 요약부터 읽고 상세는 펼칠 때 가져오는 방향으로 설계한다. 초기 로딩이 느린 원인은 아직 측정되지 않았으며 UI 단순화만으로 해결됐다고 판단하지 않는다.

## 4. 프로젝트별 저장

프로젝트 아래 작업을 수행 순서로 보관하며, 단계·마일스톤은 작업의 별도 정보로 관리한다. 마일스톤 결과는 관련 작업 목록과 연결한다.

예시 구조(파일명/스키마 확정 전):
- project.json
- work/003-initial-search/: 작업 정보, 입력 참조, 대화, 도구 사용, 산출물, summary.md
- work/006-additional-search/: 같은 구성, 이전 작업·재탐색 이유 연결
- milestones/M1/: 결과 요약과 관련 작업 참조

기준이 되는 구조화 기록에서 UI와 읽기용 Markdown을 생성한다. 두 표현을 독립적으로 수정하지 않는다. 원문·원응답·사용자 메모·피드백은 보존하고 당시 입력 버전과 연결한다. 큰 자료를 작업마다 복제하기보다 자료 ID·버전·해시와 실제 사용한 입력을 추적할 수 있게 한다. 기준 저장소·원자적 저장·병렬 순번 발급·기존 이력 이전은 후속 명세 대상이다.

## 5. 개발 검토와 사람의 참여

사용자는 개발 중 각 수행 회차의 결과를 확인하기로 했다. 에이전트가 먼저 결론·근거·남은 문제·다음 작업을 제안하고 사람의 검토를 기다린다. 해당 결론에 의존하는 후속 작업만 대기하며 독립 작업은 계속한다.

계속 진행은 실행 흐름을 허용하는 의미이며 과학적 주장 승인과 구분한다. 수정 의견은 해당 결론 버전에 연결하고 에이전트가 새 재검토 작업에서 반영 여부와 이유를 남긴다. 무응답은 승인하지 않는다. 추후 개발 검토 모드를 꺼 자율 진행할 수 있도록 분리한다. 실제 실험 권한 등의 별도 조건은 유지한다. 이미 실행 중인 의존 작업에 피드백이 도착하는 경우의 처리 규칙은 별도 설계한다.

사람의 자료 보완 기능은 개발 검토 모드를 꺼도 유지한다.

## 6. 에이전트 역할

논의상 기본 구성은 6개 역할이다. 역할 수는 별도 모델·프로세스 수를 뜻하지 않으며 매 작업에 전원이 참여하지 않는다.

| 역할 | 책임과 산출물 |
| --- | --- |
| 조정자 | 작업 목적·담당·도구·종료 조건 설정, 결과 평가 후 다음 작업 배정과 이유 기록 |
| 자료 탐색·서지 관리 담당 | 자료 탐색·선별·확보 상태·출처·중복·미확보 경로 관리, 질문별 근거 목록 보고 |
| 분야 전문가 | 내용 해석, 가설·경쟁 설명 제안, 연구 적용 가능성 검토 |
| 평가 방법 검토자 | 비교·편향·불확실성·평가 방법·판정 기준 검토 |
| 연구 설계·실행 검토자 | 변수·대조군·측정·재현성·실행 가능성·준비 공백 검토 |
| 판단 정리 담당 | 합의와 미해결 이견, 결론의 근거·한계·후속 확인 정리 |

조정자의 작업 배정과 판단 정리 담당의 과학적 종합 책임을 구분한다. Atlas·Documents·셀프드라이빙랩은 이 6개에 포함하지 않는다. 현재 가이드는 5개 책임 역할을 설명하고, 확인한 Atlas 토론 코드에는 domain/methodology/critical 3개 검토 역할과 coordinator 담당 기록이 있다. 완성된 6개 자율 에이전트가 있다는 뜻이 아니다.

독립 초기 의견 → 상호 반박·검토 → 최종 판단의 원칙을 유지한다. 같은 입력·출처를 공유하고 의견 변경 이유와 미해결 이견을 보존한다. 단순 대화 횟수나 모델 다양성으로 충분한 검증이라고 판단하지 않는다. 역할별 프롬프트·배정/종료 조건·도구 권한·추가 라운드 규칙은 구체화가 필요하다.

## 7. 자료 수집 절차와 도구 분담

Zotero는 사용자 결정으로 도구 구성에서 제외했다. 앱·Connector와 보관 자료는 유지한다. 별도 Zotero 재구현을 목표로 하지 않는다. 서지 관리 책임은 필요하며 범용 수집 도구는 아직 선택하지 않았다.

목표는 모든 PDF 확보가 아니라 실험 계획의 중요한 선택을 설명할 근거 확보다. 초기에는 분야를 파악하고 이후에는 구체적 공백을 보완하는 탐색을 제안했다. 질문별 탐색 범위와 중단 판단은 후속 구체화 대상이다.

수집 흐름:
1. 어떤 설계 선택을 위해 무엇을 알아야 하는지 정의.
2. Atlas의 보유 자료·대체 근거 확인.
3. 외부 자료 탐색·선정, 서지와 출처 먼저 등록.
4. 접근 가능한 PDF·웹 본문·보충자료 확보.
5. 미확보 항목은 저자 공개본·저장소·대체 문헌을 확인하고 시도·실패 사유 기록.
6. Pilot이 자료·서지·분석 목적을 Atlas에 전달. Atlas가 Documents 변환을 조정하는 방향.
7. Atlas가 변환 결과와 원문 위치·한계를 연결해 분석·지식 축적.
8. Pilot 전문가가 사용 적합성을 검토하고 조정자가 후속 작업 결정.

정확한 API/MCP 요청·응답 계약과 Atlas/Documents의 현행 지원 범위는 공동 검토가 필요하다. 이 문서가 기존 계약을 대체하거나 미지원 기능을 사용 가능하게 만들지 않는다.

## 8. 확보 상태·읽은 범위·사용 판단

- 확보 상태: 서지·초록·웹 본문·PDF·보충자료 등 무엇을 보유하는가.
- 확인 범위: 실제 어디까지 읽고 추출·분석했는가.
- 사용 판단: 특정 용도에 사용/조건부 사용/보류/제외인가.

PDF 없이 웹 본문을 확보해 분석할 수 있다. PDF가 있어도 분석 전일 수 있다. 초록만으로 확인하지 못한 실험 조건을 확정하지 않는다. 변환 누락·오류를 원문에 정보가 없는 것으로 해석하지 않는다.

핵심 가설·측정·대조 조건을 결정하는 자료를 우선 확보한다. 실패 시 이미 얻은 자료를 보존하고 재개 지점을 남긴다. 같은 경로를 이유 없이 반복하지 않는다. 확보 가능한 근거가 부족하면 대체 설계나 판단 보류를 제안한다. 해결되지 않는 핵심 자료는 사용자에게 확보 요청하는 방안을 제안했다. 임의 논문 수·시간 제한을 새로 두지 않는다.

## 9. 수집 전용 상세와 사용자 원문 제공

바깥 스택·공통 상세 구조를 유지하되, 수집 카드 안에는 자료 목록이 중심이 된다. 각 행에서 자료 제목, 확보 상태, 확인 범위, 다음 조치를 본다. 자료를 열면 필요한 이유·시도 경로·사용 판단·파일·Atlas 결과·연결된 대화/도구를 확인한다.

사용자는 기존 미확보 자료에 PDF 또는 원문 주소를 추가할 수 있어야 한다. 새 논문도 후보로 추가할 수 있다. 관련성 검토를 건너뛰지 않는다.

입력 후: 파일/주소 접수 → 기존 자료와 일치·중복 확인 → 불명확하면 사용자 확인 → 사용자 제공 출처·시각·버전 기록 → Atlas 변환/분석 → 막혀 있던 질문 재검토 → 해결된 내용과 남은 문제 알림. URL 입력은 본문 확보 성공을 뜻하지 않는다. 파일 추가가 검증·단계 완료를 대신하지 않는다. 사용자 제공을 에이전트의 자율 수집 성공으로 기록하지 않는다.

파일명은 읽기 쉽게 정리하지만 내부 자료 ID·출처·버전·해시를 식별 기준으로 유지한다. 재분석해도 과거 판단이 사용한 버전을 보존한다.

## 10. 검증 사례와 후속 설계 순서

실제로 확인한 것은 Polybot 한 건의 Crossref 서지와 PDF 직접 확보 및 Zotero 로컬 API 등록이다. Connector 자동 수집은 확인하지 못했다. Zotero 제외는 이 검증 이후 결정했다. 범용 수집·Documents·Atlas 전체 자동 연결이 검증된 것은 아니다.

구현 전 설계를 다음 단위로 나눈다.
1. 공통 작업 기록·의존성·상태·개발 검토: UI와 실행이 공유할 기준.
2. 수집·수동 보완·Atlas/Documents 연결: 자료 식별·접수·변환·재개 계약.
3. 에이전트 실행: 역할별 입력·도구·산출물·종료/추가 검토 판단.
4. 스택 UI: 실제 기록의 요약/상세 조회, 수집 목록, 마일스톤 결과.

첫 검증 시나리오 제안: 설계 질문 설정 → 초기 탐색 → 원문 일부 확보 실패 → 사용자가 해당 자료 보완 → Atlas 분석 → 에이전트 검토 → 부족한 근거로 추가 탐색 제안 → 개발 검토 → 후속 작업. 네 영역을 최소 범위로 연결해 확인한다.

완료 판단에는 단계/순서 분리, 병렬 순서 고정과 의존 대기, 과거 결과 보존, 미확보·부분 변환, 중복 입력·재시도, 사용자 자료 연결, API 요청과 결과 추적, M1 완료와 실험 실행 분리, 실제 초기 로딩 측정을 포함한다. 구체 테스트와 성능 목표는 설계 확정 후 작업 계획에서 정한다.
