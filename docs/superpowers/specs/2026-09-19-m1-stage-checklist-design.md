# M1 단계별 통합 실행·점검 기준

상태: 검토용 설계 초안. 아래 체크박스는 앞으로 구현·실행 시 확인할 기준이며 통과 기록이 아니다. 코드·운영 서비스·연구 상태는 변경하지 않았다.

## 1. 범위와 연결 원칙

연구 경로 M1의 목표는 연구 질문에서 실험 설계·착수 준비·인계 자료까지 마련하는 것이다. 보고서/사업 계획서 경로는 별도의 목적별 계약을 적용하며 이 실험 체크리스트를 그대로 강제하지 않는다. 가상 설계 완료와 실제 실험 착수 가능을 구분한다.

기존 scope/questions/search/screen/collect/extract/synthesize/hypothesize/review에 experiment_design/readiness를 포함한 11개 논리 단계를 정리한다. 이는 현행 엔진이 11단계를 지원한다는 뜻이 아니다. 단계 종류와 수행 순서를 분리하고 같은 단계의 반복은 별도 attempt로 보존한다.

문서 체크리스트만 두는 방식은 실행 누락을 막지 못한다. 단계마다 별도 실행기를 만드는 방식은 모델·훅·UI가 다시 갈라진다. 권고 방식은 **공통 실행 기록과 검사 엔진 + 단계별 계약**이다. 모든 요청 경로(CLI/API/MCP/UI)에 동일한 채택 검사를 적용한다.

## 2. 하나의 단계 실행 기록

각 실행은 project/milestone/step/work/attempt/generation 식별자 아래 다음을 묶는다.

- 사용자 목적·이번 목적·변경 가능한 판단·범위·계약 버전.
- 선행 결과와 사용자 피드백의 고정 참조, 자료 원형·버전·읽은 범위, 변경분과 열린 문제.
- 역할별 페르소나·책임·허용 도구·독립 공개 범위·모델 프로필 snapshot.
- 시작 검사 결과, 실제 역할 실행·도구·발언·진행 이벤트, 출력 원형.
- 종료 검사·의미 검토·채택 판단·보류 범위·후속 배정 및 접수 확인.

검사 결과에는 check_id/version, 판정, 이유, 확인한 자료·위치, 검사 수행자, 영향받는 판단, 보완 작업, 시각을 기록한다. 자동 구조 검사와 실제 의미 검토 결과를 별도 보존한다. 실행하지 않은 검사는 미실행이며 실패나 통과로 추정하지 않는다.

### 공통 시작 훅

- [ ] 프로젝트·현재 M1·사용자 목적 버전·자율 실행 범위를 확인했다.
- [ ] 이번 작업의 필수 선행 결과가 채택돼 있고 영향받는 변경이 없다.
- [ ] 필수 입력 원형에 접근했고 참조·버전을 검증했다. 없는 자료를 제공됐다고 표시하지 않았다.
- [ ] 목적·페르소나·이전 결론·변경분·산출물·완료 기준을 실제 작업 입력에 넣었다.
- [ ] 역할별 모델·추론 설정을 해석해 실행 snapshot으로 고정했고 필요한 기능을 지원한다.
- [ ] 동일 작업의 실행·접수·완료 기록을 조회해 중복 요청을 막았다.
- [ ] 시작 검사와 실행 접수 결과를 저장했다. 실제 워커가 없으면 실행 중으로 표시하지 않는다.

### 공통 종료 훅

- [ ] 출력 원형·구조·자료 참조·사용 버전과 실제 실행 기록을 확인했다.
- [ ] 사실·문헌 보고·해석·가정·제안·가상 결과를 구분했다.
- [ ] 해당 단계의 필수 검토가 실제로 수행됐고 주요 이견·반론이 보존됐다.
- [ ] 입력·정책·배정·세대가 아직 유효하다. 오래된 결과는 보존하되 채택하지 않는다.
- [ ] 단계 고유 완료 기준을 검사하고 남은 문제의 영향과 허용/보류할 행동을 정했다.
- [ ] 사용자가 승인하지 않은 내용을 승인으로 기록하지 않았다.
- [ ] 다음 작업·수신자·입력·완료 조건을 영속 배정했다. 배정과 실제 접수를 구분했다.

통과는 다음 작업의 접수까지 추적한다. 보완은 기존 attempt를 보존하고 새 attempt와 이유를 연결한다. 외부 대기는 요청 ID·마지막 관찰·다음 관찰 조건을 기록한다. 재시작 시 원장을 대조하며 결과가 있으면 재사용하고 실행 여부 불명확 시 상태 확인을 먼저 한다. 횟수나 시간 소진으로 강제 통과하지 않는다.

## 3. 모델·추론·페르소나 기준

SSO 기준: `/Users/jspark/orca/projects/sso/docs/llm-connection-design.md`. 이는 제품 방향 합의 문서이며 배포 완료 증거가 아니다.

Pilot 제안 우선순위는 작업별 명시 설정 → 단계·역할 기능 설정 → 앱 기본값이다. 앞의 작업별 설정은 SSO의 기능별 → 앱 기본값을 구체화한 Pilot 확장안이다. 어느 경로든 최종 공급자/실행 방식/실행 위치/정확한 모델 ID/추론 설정/프로필 버전을 시작 전에 고정한다. 비밀 값은 저장하지 않고 인증 참조만 사용한다. 실행 중 설정 변경은 다음 작업에 적용하고 자동 대체 모델 사용은 하지 않는다.

아래 표준/심층은 설계상 작업 등급이지 제공자 API의 실제 값이 아니다. 프로필에서 지원되는 reasoning 값·예산으로 매핑해야 한다. 미지원이면 조용히 무시하지 않고 설정 보완으로 둔다. 요청 설정·호출 적용 증거·제공자가 보고한 실행 정보는 구분하며 제공자가 노출하지 않는 정보는 미확인으로 남긴다. 추론 깊이는 내부 사고 전문을 저장하라는 뜻이 아니다.

| 프로필 | 담당과 페르소나 | 요청 추론 등급 | 현재 바인딩 상태 |
|---|---|---|---|
| P-COORD | 조정자: 원래 목적, 판단 영향, 다음 행동과 범위를 관리 | 표준; 핵심 채택은 심층 | 실제 모델/공급자 값 연결 필요 |
| P-SEARCH | 탐색자: 반대 근거도 찾고 확보·읽기·사용 판단을 구분 | 표준 | 동일 |
| P-DOMAIN | 분야 검토자: 재료·공정·기전의 성립 조건과 적용 범위 검토 | 심층 | 동일 |
| P-METHOD | 방법 검토자: 비교 가능성·통계·반증·측정 적합성 검토 | 심층 | 동일 |
| P-CRITIC | 비판 검토자: 반례·혼동 요인·근거 비약을 검토, 무조건 반대하지 않음 | 심층 | 동일 |
| P-EXEC | 실행 검토자: 장비·데이터·추적·실패 복구·실행 가능성 검토 | 심층 | 동일 |

모든 역할을 항상 실행하지 않는다. 아래 단계의 작성 책임과 필수 검토만 적용한다. 중요한 가설·설계·최종 판단은 작성자의 자기평가로 대체하지 않는다. 독립 초기 의견 → 상호 검토 → 조정자의 판단을 보존한다. 추가 라운드는 새 근거·판단에 영향을 주는 충돌이 있을 때 배정하며 합의를 강제하지 않는다. 이견이 없거나 추가 검토가 불필요하면 이유와 함께 종료할 수 있다.

## 4. 단계별 체크리스트

모든 단계는 공통 훅을 상속한다. 아래 시작/끝 항목은 단계별 추가 기준이다.

### 01. 연구 범위 — scope

목적: 사용자 요청을 유지하면서 조사할 범위와 M1 도달점을 정한다.
입력: 원래 요청·제약·목적 경로·사용자 피드백. 담당: P-COORD 표준, 큰 범위 변경 시 P-DOMAIN 심층 검토.

시작:
- [ ] 연구/평가/계획 경로와 가상 설계/실제 착수 목표를 구분했다.
- [ ] 이전 프로젝트의 결론이나 완료 상태를 새 연구에 자동 승계하지 않았다.
끝:
- [ ] 대상·포함/제외 범위·제약·M1 산출물을 명시했다.
- [ ] 지금 정해야 할 것과 문헌을 보고 정할 것을 구분했다.
- [ ] 범위가 원래 요청과 일치하며 축소·변경 이유가 있다.
산출물: 범위 카드와 미정 사항. 통과 → 02. 핵심 목적 불명확 → 해당 질문 보완. 실제로 필요한 사용자 답만 기다린다.

### 02. 연구 질문 — questions

목적: 어떤 비교와 판단을 할지 구체화한다.
입력: 채택 범위 카드. 담당: P-COORD 표준 작성, P-METHOD 심층으로 질문의 판별 가능성 검토.

시작:
- [ ] 질문이 범위와 연결되고 범위 변경 필요 여부를 확인했다.
끝:
- [ ] 대상·주요 변수/비교·평가 항목·조건이 드러난다.
- [ ] 무엇을 알아야 답할 수 있고 검색 결과가 어떤 결정을 바꿀지 명시했다.
- [ ] 아직 근거가 없는 방향·효과 크기를 사실로 전제하지 않았다.
산출물: 연구 질문·하위 질문·자료 요구표. 통과 → 03. 범위와 충돌 → 01.

### 03. 문헌 검색 — search

목적: 질문에 답할 후보와 빠진 근거를 찾는다.
입력: 질문·자료 요구·기존 Atlas 보유 자료 참조. 담당: P-SEARCH 표준; P-COORD 표준이 검색 범위 적합성을 확인.

시작:
- [ ] 기존 자료·버전을 조회하거나 조회 불가를 기록했다.
- [ ] 검색어·검색 경로·핵심 및 반대 근거 요구를 정했다.
끝:
- [ ] 실제 질의·도구·시각·검색 결과·식별 가능한 출처를 기록했다.
- [ ] 후보, 원문 확보, 실제 읽음 상태를 구분했다.
- [ ] 단순 개수가 아니라 자료 요구별 후보/공백을 설명했다.
산출물: 검색 기록·후보 목록·공백. 후보별 04로 이동 가능하며 검색 전체 종료를 기다릴 필요는 없다. 공백은 구체 질의를 바꿔 재탐색한다.

### 04. 문헌 선정 — screen

목적: 이번 질문의 어떤 용도에 검토할 자료인지 정한다.
입력: 후보·초록/확인 가능한 본문·선정 기준. 담당: P-SEARCH 표준, 핵심 포함/제외 판단은 P-DOMAIN 심층.

시작:
- [ ] 어떤 범위까지 읽었는지 확인했다.
끝:
- [ ] 소재·공정·변수·평가 항목의 관련성을 판단했다.
- [ ] 직접 비교/배경/반례/보류/제외 이유를 남겼다.
- [ ] DOI·프리프린트·출판본 관계를 확인하고 같은 원천을 독립 근거로 세지 않았다.
- [ ] 원문 접근 실패나 불리한 결과만으로 과학적 제외하지 않았다.
산출물: 용도별 선정표. 통과 → 05. 적합 후보 없음 → 03. 기준 변경 → 02 또는 01 재검토.

### 05. 원문 수집 — collect

목적: 분석할 원형과 서지·버전을 확보한다.
입력: 선정 자료·원문 요구 범위. 담당: P-SEARCH 표준, 다운로드/해시 확인은 도구.

시작:
- [ ] 이미 확보·접수한 원형이 있는지 확인했다.
끝:
- [ ] 실제 파일 또는 접근 가능한 본문·주소·버전·해시를 연결했다.
- [ ] 본문·보충자료·정정본의 관계와 누락을 기록했다.
- [ ] 접근 실패·대체 경로·사용자 제공 필요를 보존했다.
- [ ] 없는 PDF나 읽지 않은 본문을 확보·분석 완료로 표시하지 않았다.
산출물: 원문 목록과 회수 가능한 참조. 사용 가능한 자료 → 06. 핵심 미확보 → 대체 검색/자료 요청, 독립 자료는 계속 진행.

### 06. 변환·지식화·근거 추출 — extract

목적: 원문을 Documents로 처리하고 Atlas에 축적된 분석 결과를 검증해 연구 입력으로 회수한다.
입력: 원문·서지·버전·구체 추출 질문. 담당: P-COORD 표준 의뢰, Documents/Atlas 외부 작업, P-DOMAIN 심층 사용 범위 검토.

시작:
- [ ] Documents/Atlas 기능·인증 consumer·instance·project·중복 요청을 확인했다.
- [ ] Pilot의 Documents 제출과 Atlas import 요청을 공급자 원형 식별자로 연결했다.
끝:
- [ ] task/receipt/import/job/event를 원래 work/attempt와 연결했다.
- [ ] 변환 결과에 본문·표·그림 해석·보충자료의 포함/누락이 표시돼 있다.
- [ ] Atlas 결과와 사용 원형·위치·해시·읽은 범위를 회수·보존했다.
- [ ] partial의 기술 결함과 과학적 공백을 구분하고 해당 용도 사용을 판단했다.
- [ ] ACK는 원형 수신 의미로만 기록했다. ACK나 위키 저장을 검토 완료로 승격하지 않았다.
- [ ] ask와 위키 반영은 계약이 다른 작업으로 기록하고, 현재 제공되는 계약을 사용했다.
산출물: 자료별 근거 카드·개별 검토·누락 목록. 도착 자료부터 개별 검토, 준비된 고정 묶음은 07로 전달. 장애는 원래 요청 조회·복구, 과학 공백은 03~05로 보완. 일반 ask에 import 이벤트 의미를 적용하지 않는다.

### 07. 근거 종합 — synthesize

목적: 여러 자료가 질문에 무엇을 말하고 무엇을 말하지 못하는지 판단한다.
입력: 자료별 검토와 버전 고정 묶음·대기 자료 목록. 담당: P-DOMAIN/P-METHOD 독립 심층 검토, P-COORD 심층 종합; 핵심 충돌 시 P-CRITIC 추가.

시작:
- [ ] 묶음 범위·필수 자료·미도착 자료가 명시돼 있다.
- [ ] Atlas 분석과 원문, Pilot 해석을 구분했다.
끝:
- [ ] 주장마다 근거 위치·조건·반론·불확실성을 연결했다.
- [ ] 함량·공정·단위·시편·배향·데이터 원천 차이로 비교 가능한 범위를 구분했다.
- [ ] 동일 원천 중복·상반 결과·선택 편향을 검토했다.
- [ ] 남은 공백이 가설 초안 진행을 막는지, 실험 질문으로 남길지 판단했다.
산출물: 근거 종합표·채택 판단·미해결 문제. 통과 → 08. 자료 공백 → 03~06. 해석 차이 → 범위를 정한 추가 검토. 새 자료 도착 시 영향받는 주장만 재검토.

### 08. 가설과 반증 — hypothesize

목적: 근거에서 검증 가능한 가설과 경쟁 설명을 만든다.
입력: 채택 근거 종합·연구 질문·한계. 담당: P-DOMAIN 심층 작성, P-METHOD/P-CRITIC 독립 심층 검토, P-COORD 심층 채택.

시작:
- [ ] 가설에 사용하는 자료가 해당 용도로 사용 가능하다.
끝:
- [ ] 가설·경쟁 설명·관측 예측·지지/반증/판단 불가 조건이 있다.
- [ ] 문헌이 지지한 사실과 새 가설을 분리했다.
- [ ] 예상 효과와 판정 규칙을 혼동하지 않았다.
- [ ] 기전 판별인지 성능 비교인지 구분하고 실험으로 구별 가능한지 검토했다.
산출물: 가설 카드·예측/반증표·검토와 채택 이유. 통과 → 09. 근거 부족 → 07 또는 자료 보완. 판별 불가 → 02/08 범위 조정.

### 09. 실험 설계 — experiment_design

목적: 가설을 시험할 비교·측정·분석 계획을 만든다.
입력: 가설·반증 조건·현실 제약. 담당: P-METHOD/P-EXEC 심층 설계, P-DOMAIN/P-CRITIC 심층 검토, P-COORD 심층 채택.

시작:
- [ ] 가상 설계인지 실제 실행 명세인지 표시했다.
끝:
- [ ] 변수·수준·대조군·독립 반복·무작위화/블록·혼동 요인 통제를 정의했다.
- [ ] 시편/데이터 단위·측정법·단위·주 평가 항목·분석법을 정의했다.
- [ ] 표본 수는 근거 또는 예비시험 기반 결정 방법이 있다. 임의 수치를 확정하지 않았다.
- [ ] 결측·실패·이상치·불확실성·성공/중단 기준을 사전에 정했다.
- [ ] 데이터 연구면 분할·누출 방지·비교 기준을 적용하고, 비해당 검사는 이유를 남겼다.
산출물: 실험 계획·분석 계획·검토 기록. 통과 → 10. 가설 판별 불가 → 08, 근거 부족 → 07/자료 보완.

### 10. 착수 준비와 인계 자료 — readiness

목적: 실행 담당이 계획을 재현할 수 있게 자료와 조건을 준비한다.
입력: 채택 설계·실행 환경과 제약. 담당: P-EXEC 심층 작성, P-METHOD 심층 데이터 규격 점검, P-COORD 표준 조정.

시작:
- [ ] 장비·재료·코드·환경·예산·일정·안전·권한 중 적용 항목을 구분했다.
끝:
- [ ] 작업·시료·시도·원자료를 연결할 식별자와 CSV/결과 규격이 있다.
- [ ] 단위·필수 열·결측·실패 이유·원자료 위치·버전을 규정했다.
- [ ] 실행 순서·중단·실패·재시도·복구·수신자 책임이 명확하다.
- [ ] 가상 예제로 규격을 점검했다면 합성임을 표시했다. 실제 장비 연결·실험 성공과 구분했다.
- [ ] 실증 전 필수 조건을 별도로 표시했고 미충족 상태를 준비 완료로 감추지 않았다.
산출물: 실행 패키지·데이터 사전·준비 점검표·미충족 조건. 통과 → 11. 실행 불가능 → 09 수정. 가상 M1의 허용 범위 밖 실증 조건은 명시적으로 남긴다.

### 11. 최종 검토와 M1 종료 — review

목적: 전체 판단 사슬과 승인된 M1 도달점 충족을 확인한다.
입력: 01~10의 채택 산출물·필수 검사·미해결 문제·실행 원장. 담당: P-DOMAIN/P-METHOD/P-EXEC 필요한 부분 독립 심층 검토, P-COORD 심층 종합. 유효한 기존 검토는 재사용하고 변경분을 검사한다.

시작:
- [ ] 필수 단계별 채택/적용 제외 근거가 있다. 에피소드 종료만으로 대체하지 않았다.
끝:
- [ ] 원래 질문 → 자료 → 근거 → 가설 → 설계 → 실행 자료가 추적된다.
- [ ] 핵심 반론·남은 질문·영향·담당·처리 조건이 정리됐다.
- [ ] 필수 진행 중 작업·고아 요청·늦은 응답의 처리 방침이 있다.
- [ ] M1 목표 범위에 필요한 검사와 의미 검토가 실제로 통과했다.
- [ ] 가상 설계 완료·실제 착수 가능·M2 인계 수락을 구분했다.
- [ ] 최종 산출물 버전과 인계 대상·수락 조건을 고정했다.
산출물: M1 결과 패키지·최종 판단·잔여 조건. 통과 → 현재 M1 자율 실행 종료. M2 실행/수락을 자동 생성하지 않는다. 실패 → 영향받는 단계에 보완 배정하고 무관한 결과는 보존한다.

## 5. 공통 산출물과 UI

Presentation 전달 패키지는 프로젝트/목적/단계/버전, 쉬운 요약, 결론, 근거와 원문 위치, 반론·한계, 결정 이유, 그림/표/데이터 참조, 역할·모델·검토 기록, 다음 행동을 포함한다. 실제 파일 형식과 수신 계약은 별도 정렬이 필요하며 이미 Presentation이 수락한 포맷으로 주장하지 않는다.

UI는 실행 원장을 투영한다. 단계별로 현재 상태와 이유·목적·산출물·다음 작업을 먼저 보여주고 시작 검사/종료 검사, 역할·모델·추론 설정, 실제 대화, 도구 사용, 이력은 펼쳐 본다. 내부 사고 전문 대신 제출된 발언과 판단 근거를 제공한다. 원문과 쉬운 해설은 분리한다. 피드백은 결과 버전에 연결하고 기본적으로 매 단계 사용자 승인을 기다리지 않는다. 별도 승인 모드가 명시됐다면 그 정책을 따른다.

상태는 준비/실행 접수/실행 중/외부 대기/보완 필요/채택/보류/실행 상태 확인 필요를 구분한다. 마지막 관측 시각과 다음 행동을 표시하고 UI에만 저장한 완료 상태를 만들지 않는다.

## 6. 구현 수락 체크리스트

- [ ] 각 단계에서 필수 입력 하나를 제거하면 해당 작업만 차단되고 이유가 UI에 보인다.
- [ ] 미설정 모델·지원하지 않는 추론 설정이 기본값으로 조용히 실행되지 않는다.
- [ ] 실제 호출 설정과 실행 기록이 일치하고 실행 중 프로필 변경이 기존 시도에 영향을 주지 않는다.
- [ ] 모든 단계에서 출력 누락·근거 오류·필수 검토 누락이 채택되지 않는다.
- [ ] 정상 종료 후 다음 작업이 영속 배정되고 실제 접수 여부까지 확인된다.
- [ ] 입력 변경·실패·재시작·응답 유실·중복 이벤트·늦은 결과에서도 원형과 시도 이력이 유지된다.
- [ ] Documents/Atlas는 수신→검토→원래 업무 반환이 이어지고 ACK만으로 연구가 완료되지 않는다.
- [ ] 모델 독립 초기 의견이 전원 제출 전에 다른 초기 검토자에게 노출되지 않는다.
- [ ] 비핵심 미정 사항은 후속 과제로 남기고 진행할 수 있다. 핵심 결함만 영향 범위를 차단한다.
- [ ] API/CLI/UI 어느 경로로도 동일 검사를 우회하지 못한다.
- [ ] 연구 실행 중 검사·발언·도구·대기 이유가 UI에 기록된다.
- [ ] 합성 종단 시험 후 실제 좁은 연구 한 건을 원문부터 승인된 M1 종료까지 검증한다.

## 7. 현재 구현과의 차이 및 개발 순서

현재 확인된 새 lifecycle 계약은 evidence_review만 허용한다. 역할별 모델은 새 host에서 codex-cli-default-unverified로 기록되며, 전 단계 계약·후속 자동 실행·모델 프로필 연결이 완료된 상태가 아니다. 기존 Documents/Atlas 기능의 개별 시험을 이 전체 흐름 검증으로 대체하지 않는다.

1. 이 계약의 단계 ID·검사 ID·모델 바인딩·산출물 필드를 확정한다.
2. 공통 실행 기록 위에 01→02→03 실제 접수까지 모델·훅·UI·재개를 세로로 연결해 검증한다.
3. 04~06과 Documents/Atlas 왕복·개별 검토를 같은 구조에 연결한다.
4. 07~10의 의미 검토·되돌림·실행 패키지를 연결한다.
5. 11의 마일스톤 검사와 전체 종단 시험을 통과한 뒤 실제 연구에 적용한다.

단계별 추적표에는 설계/구현/호출 연결/자동 시험/실제 실행/UI 확인을 각각 기록한다. 이 문서 작성으로 어느 항목도 구현 완료로 승격하지 않는다.
