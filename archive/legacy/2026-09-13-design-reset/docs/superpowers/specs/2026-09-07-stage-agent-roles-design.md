# 단계별 에이전트 역할 보완 설계

> 아카이브: 이전 단계 구조 또는 철회한 제안의 개발 이력이다. 새 개발의 작업 지시로 사용하지 않는다. [현재 설계 정리](../../../../../../docs/superpowers/specs/2026-09-13-pilot-autonomous-research-design.md).

작성일: 2026-09-07
기준: main `fd852f582d1ca28ed28ca32219a877fea8473a96`
상태: 사용자와 합의한 보완 방향을 구체화한 설계. 본 문서 확인 후 A 구현 계획 작성·실행으로 진행한다.

## 1. 목적과 현황

연구 판단은 Codex 에이전트가 수행하고, Python CLI는 근거·절차·무결성·권한을 검증한다. 외부 LLM API나 별도 모델 실행 프로그램을 도입하지 않는다.

현재 1~11단계는 주로 단일 Codex 작성과 로컬 검증, 12단계는 승인된 실행의 전달·등록이다. 13단계는 3판단 역할과 비투표 조정자·구현 담당, 14~15단계는 3판단 역할과 비투표 조정자가 있다. 역할 이름만으로 실제 독립 검토나 과학적 품질이 입증되지는 않는다.

이번 보완의 목표는 단계마다 서로 다른 검토 관점과 책임을 부여하고, 중요한 판단에서 독립 검토와 협의 기록을 확보하는 것이다. 개발을 수행하는 보조 에이전트와 ResearchClaw 사용 시 연구를 수행하는 역할은 서로 다른 개념이다.

## 2. 접근 방식 선택

- 권장: 공통 역할 정의와 단계 프로필을 만든 뒤, 기존 협의 구현을 참고해 7~9단계부터 순차 연결한다. 단계별 절차의 차이를 유지하며 공통 요소만 재사용한다.
- 대안: 스킬 문구만 일괄 보강한다. 빠르지만 협의 기록 없이도 진행되는 현재의 한계를 해결하지 못한다.
- 대안: 1~15단계를 하나의 범용 협의 엔진으로 즉시 교체한다. 승인·등록·복구·기존 증거 형식에 미치는 영향이 크므로 채택하지 않는다.

공통 정의의 존재, 스킬의 역할 배정 지침, 실제 협의 기록 등록, 실제 에이전트 실행 확인을 구분해 보고한다. 앞의 하나만 구현하고 나머지까지 완료됐다고 표시하지 않는다.

## 3. 변경 불가 원칙

- 외부 LLM API 호출, API 키 요구, 별도 모델 프로세스 실행을 추가하지 않는다.
- 새 판단은 현재 Codex와 허용된 도구로 수행한다. 모델·제공자·요금제를 코드가 결정하지 않는다.
- 기존 완료 단계, 원본 연구 프로젝트, 승인 기록, 불변 증거와 파일 해시를 자동으로 수정하지 않는다.
- 사용자 승인·반려·실행 확인과 기존 예산·경로 제한을 유지한다. 협의는 실행 승인 대체 수단이 아니다.
- 형식 통과, 점수 개선, 에이전트 수를 과학적 타당성 증명으로 표시하지 않는다.
- 자동 점수로 연구 방향을 선택하지 않는다. 법칙·수치·해시·예산 검사는 코드의 정당한 책임으로 유지한다.
- 미해결 이견은 실제 기록대로 남긴다. 조정자가 타인의 의견·응답을 작성하거나 합의를 조작하지 않는다.
- 16단계 개발, 기존 연구의 재실험, laboratory/policy_evidence 실행 지원 확대는 이번 보완 범위 밖이다.

## 4. 공통 역할과 페르소나

주요 연구 판단은 `domain`, `methodology`, `critical_reproducibility`의 세 독립 관점과 비투표 `coordinator`를 기본으로 한다. 10·13단계의 `implementation`은 평가 역할과 분리한다. 수집·추출·자원·실행 단계에는 `worker`와 독립 `verifier`를 사용하고, 필요할 때만 별도 연구 판단 절차로 넘긴다. 숫자는 논리적 역할 수이며 동시 실행 수가 아니다.

페르소나는 가상의 경력·성격이 아니라 다음을 포함한다.

1. 역할 ID와 책임: 어떤 관점의 판단 또는 작업을 맡는가.
2. 필수 질문: 해당 단계에서 반드시 확인할 구체적인 쟁점.
3. 판단 기준: 근거가 뒷받침해야 할 조건과 반증·반대 설명.
4. 근거 사용: 패킷이 허용한 입력만 사용하고, 관측·파생 계산·추론·미확인을 구분.
5. 권한 제한: 작성·검토·조정·실행·승인 중 맡지 않은 권한을 행사하지 않음.
6. 출력 요구: 판단, 근거, 한계, 다른 역할에 대한 질문을 단계별 계약에 맞게 작성.

조정자는 초기 독립 검토에 자신의 결론을 미리 주입하지 않고, 모든 초기 제출 후 공개·응답을 진행한다. 작성·구현 담당은 자신의 산출물을 단독으로 승인하지 않는다. 역할을 수행할 수 없으면 그 사실을 알리고, 한 에이전트가 여러 독립 생산자를 흉내 내지 않는다.

## 5. 단계별 목표 프로필

다음은 보완 완료 후의 목표다. A에서는 프로필만 제공하고 신규 협의 등록이나 진행 차단을 구현하지 않는다.

| 단계 | 목표 구성 | 단계별 필수 쟁점 |
| --- | --- | --- |
| 1 | 3판단 + 조정 | 사용자 요구와 가정, 분야 가치, 목표·비목표, 자원에 맞는 성공 조건 |
| 2 | 3판단 + 조정 | 연구 질문 간 관계, 대안 문제 구조, 누락·인과 혼동 |
| 3 | 3판단 + 조정 | 분야 용어, 재현 가능한 검색식·범위, 검색·출판 편향 |
| 4 | 작업 + 독립 확인 | 실제 출처·제목·식별자 일치, 중복, 접근 실패, 수집과 선별의 분리 |
| 5 | 3판단 + 조정 | 포함·제외 근거, 연구 방법 적합성, 반증 문헌·경계 사례와 사용자 승인 |
| 6 | 작업 + 독립 확인 | 원문과 주장·수치·조건 대조, 원문 관측과 해석·추론의 구분 |
| 7 | 3판단 + 조정 | 근거의 일치·충돌·공백, 근거 강도, 경쟁 설명, 단순 문헌 수와 결론의 구분 |
| 8 | 3판단 + 조정 | 분야 가치, 반증 가능성, 가설 구별 관측, 기각 조건, 선정 이유 |
| 9 | 3판단 + 조정 | 대조·분할·누출, 지표·분석 계획, 재현성·실패 조건, 예산과 사용자 승인 |
| 10 | 구현 + 3판단 + 조정 | 승인 설계와 코드의 일치, 학습·예측 분리, 정적 검사와 내용 타당성의 구분 |
| 11 | 계획 작업 + 독립 확인 | 자원 추정 근거, 입력 준비, 실행 가능성, 승인 범위 내 대안 |
| 12 | 실행 지원 + 독립 확인 | 승인된 실행과 결과의 일치, 누락·실패 기록, 사용자 실행 권한과 등록 경계 |
| 13 | 기존 3판단 + 조정 + 구현 | 개선 이유, 허용 변경, 종료·후보 선택, 반대 의견과 예산 유지 |

13단계는 현재 최소 2개 일치 표의 정족수 규칙을 사용한다. 15단계는 세 최종 권고가 일치해야 합의로 등록한다. A에서는 두 정책을 그대로 설명하고 변경하지 않는다. 향후 정책 정비는 별도 승인된 설계로 다루며 과거 결정을 새 규칙으로 재판정하지 않는다. 14단계는 분석 종합이므로 방향 투표로 바꾸지 않는다.

## 6. 독립 실행과 근거 기록의 한계

후속 협의 등록에서는 실제 역할 배정 식별자, 최초 제출, 공개, 응답과 최종 기록을 연결한다. 호스트가 제공한 실제 작업 식별자를 우선하고 사용할 수 없으면 미확인으로 표시한다. 생산자 문자열만으로 독립 실행이 검증됐다고 주장하지 않는다. 호스트별 실행 기록은 출처 추적의 근거이지 과학적 독립성의 완전한 인증이 아니다.

연구 협의는 기본적으로 초기 독립 판단 후 한 차례 응답으로 제한한다. 합의 불성립이나 추가 근거 필요가 남으면 조정자가 해결된 것처럼 기록하지 않고 사용자에게 보고한다. 무제한 협의 반복, 자동 추가 실험 또는 자동 비용 증가는 허용하지 않는다.

사람이 읽는 요약은 결론, 핵심 근거, 관점 차이, 남은 한계, 다음 행동을 포함한다. 전체 역할 기록과 연결하되 짧은 요약을 불변 원문 대신 사용하지 않는다.

## 7. 구현 분할과 완료 기준

### A — 공통 역할 정의와 읽기 전용 조회: 첫 구현 단위

독립적으로 설치·시험 가능한 작은 기반을 만든다. 신규 순수 데이터 모델과 번들 프로필, 읽기 전용 CLI, 사용 지침과 테스트가 한 단위다.

- 추가 명령: `researchclaw-codex roles describe --stage 7 --json`.
- 프로젝트 경로를 받지 않으며 프로젝트 상태·파일·이벤트·승인을 생성하거나 변경하지 않는다. 에이전트 실행이나 애플리케이션 차원의 캐시 생성도 하지 않는다.
- 지원 범위는 1~15단계. 0, 16, 23, 음수 및 숫자가 아닌 입력은 exit2로 거부한다. 16단계 실행 지원으로 오해될 출력을 제공하지 않는다.
- 반환 필드: `schema_version`(1), `stage_id`, `protocol_version`(1), `activation`(`guidance_only`), `mode`, `roles`, `existing_protocol`.
- `mode`: 표의 구성에 따라 `judgment_council`, `work_and_verify`, `implementation_council` 중 하나.
- 각 역할 레코드: `role_id`, `responsibility`, `required_questions`, `judgment_criteria`, `authority_limits`. 질문·기준은 해당 단계에 구체적이어야 한다.
- `existing_protocol`: 1~11은 `single_author_validation`, 12는 `user_execution_handoff`, 13은 `registered_refinement_council`, 14는 `registered_analysis_council`, 15는 `registered_decision_council`로 기존 구현을 설명한다. 이는 개별 프로젝트의 완료·실행 사실을 인증하는 필드가 아니다.
- 중복 역할 ID, 빈 질문·기준·책임, 미지원 모드·필드·버전은 거부한다. 반환 데이터의 변경이 이후 조회를 오염시키지 않도록 한다.
- JSON은 하나의 값만 stdout에 출력하고 오류는 stderr/exit2로 보고한다. 모델 설정·키·외부 서비스 초기화가 없어야 한다.
- 번들 지침에서는 조회 결과가 과거 승인이나 현재 단계 패킷보다 우선하지 않음을 명시한다. A만 설치한 상태에서 1~12단계에 새 협의 산출물을 임의로 작성하지 않는다.

예상 파일 책임:

- 신규 `researchclaw/core/agent_roles.py`: 역할 프로필을 읽고 검증·반환하는 로직. 프로젝트 상태나 역할 실행기를 소유하지 않는다.
- 신규 `researchclaw/core/data/agent_roles.json`: 버전이 지정된 1~15단계 역할·질문·기준 데이터.
- 수정 `researchclaw/codex/cli.py`: 프로젝트 로드 없이 조회하는 서브명령 연결만 추가.
- 신규 `skills/researchclaw/references/agent-roles.md`: 조회 사용법, 안내와 등록의 차이, 역할별 권한과 실행 기록 한계.
- 수정 `skills/researchclaw/SKILL.md`: 공통 역할 참고 자료 연결. 기존 13~15단계 규칙과 사용자 확인은 유지.
- 신규 `tests/codex_native/test_agent_roles.py`, 기존 `test_cli.py`와 `test_plugin_package.py`: 데이터·조회·설치 패키징 검증.

A에서는 `TaskPacket`, `ProjectState`, 기존 산출물 JSON, 등록 명령, 승인·복구·협의 판정 규칙을 변경하지 않는다. 새 프로필을 과거 해시 패킷에 끼워 넣지 않는다.

### B — 7~9단계 협의의 실제 연결: 두 번째 설계·구현 단위

A를 전제로 7단계부터 하나씩 연결한다. 역할별 초기 제출·공개·응답·종합, 초안 수정 후 검토 대상 해시의 일치, 미해결 상태, 사용자 요약을 등록 경로에 연결한다. 실제 검토가 없는 상태에서 새 프로토콜의 단계 완료로 넘어갈 수 없어야 한다.

이 단위의 구현 전에는 독립된 상세 설계에서 새 기록 경로·버전·초안 변경 시 무효화 범위·진행 조건을 확정한다. B의 인터페이스는 이번 A 구현 계약에 포함하지 않는다. 이전 완료 프로젝트와 새 프로토콜 프로젝트를 구분하며 강제 마이그레이션하지 않는다.

B 완료는 문구나 테스트 fixture뿐 아니라, 실제 Codex 역할 분리로 수행한 작은 7~9단계 수용 검사와 사용자 요약 확인을 포함한다. 협의 불성립 사례도 확인한다.

### C — 5·6·10단계 독립 검증 연결

문헌 선별, 원문 대조, 코드 작성자와 검토자 분리를 적용한다. 형식 검증이 과학적 타당성 판단을 대체하지 않도록 한다. 코드 실행 권한은 확대하지 않는다.

### D — 1~4·11~12단계 보완

목표·문제·검색의 협의와 수집·자원·실행의 독립 확인을 연결한다. 작업 자체를 매번 3인 협의로 바꾸지 않는다.

### E — 13~15단계와 사용자 표시 정비

기존 기능은 유지하며 단계별 페르소나·실행 기록·짧은 요약을 정비한다. 정족수 정책 변경은 별도 결정이다. 이후 16단계는 검증된 공통 구조를 사용하도록 별도 설계한다.

각 단위는 독립적으로 검증 가능한 변경으로 끝내며, 전체가 완료되기 전에 1~15단계 전면 적용으로 보고하지 않는다.

## 8. 검증·비용 관리

A는 데이터·CLI·패키징 중심의 빠른 검사로 개발한다. 역할별 질문과 권한을 구체적으로 단언하는 테스트를 먼저 작성하고, 미지원 단계·잘못된 데이터·반복 조회 불변성·프로젝트 없는 조회·설치본 조회를 확인한다.

기존 단계 준비·등록·승인 테스트는 영향을 받는 묶음으로 확인한다. 수정마다 수천 개의 전체 검사를 반복하지 않고, 기능 묶음이 안정된 통합 시점에서 전체 회귀 검사를 실행한다. 최종 기록에는 검사 대상 커밋, 실행 명령, 통과·실패·건너뜀을 구별한다. uv 임시 환경을 사용하는 전체 검사 중 다른 uv 작업을 겹치지 않는다.

내용 품질 평가는 B부터 별도 수행한다. 모순된 근거, 상관과 인과의 혼동, 반증 불가능한 가설, 누출 위험 설계를 포함한 작은 사례로 역할별 지적과 최종 수정의 근거를 확인한다. 평가자가 결과를 검토하며, 특정 문구나 점수의 자동 통과를 연구 판단으로 대체하지 않는다. 테스트용 기록을 실제 독립 에이전트 실행 기록으로 취급하지 않는다.

## 9. 승인·배포 경계

앞서 제안한 전체 보완 방향에 대한 사용자 동의를 바탕으로 작성했다. 이 설계 문서 확인 후 A의 실행 가능한 상세 구현 계획을 작성한다. B~E는 해당 단위의 인터페이스와 기존 상태 호환성을 각각 확정한 뒤 진행한다.
